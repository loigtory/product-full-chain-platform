> 分类：System Iteration Requirement / strict / 设计阶段

> 日期：2026-09-07  
> 确认方式：当前协作会话明确回复“同意”  
> Parent POD / Milestone：`POD-PFC-001 / M2`  
> 影响 CAP：`CAP-PFC-01～05`，代表性薄切优先覆盖 `CAP-PFC-01/02/03/04`  
> 权威产品范围：主 Spec `V0.1/R3`，保持 5 个 CAP、26 个 Unit 不变  
> 当前 POD 唯一路线：`POD-PFC-001/M2/R2/standard-local-migration-authorization`

## 1. 决策摘要

PFC 的目标交互不是“传统管理后台加一个 AI 菜单”，也不是“所有工作都塞进聊天框”。目标模型确定为：

> **Agent 作业主界面 + 结构化成果画布 + 生命周期状态导航 + 可审计执行时间线。**

自然语言负责表达意图、澄清问题和调度作业；`Requirement`、`Decision`、`ArtifactVersion`、`GateRun`、`AgentRun`、`Approval` 和 `Evidence` 继续作为 PostgreSQL 中的权威业务事实。对话内容不能直接冒充阶段、版本、审批或验收结论。

本基线用于修正当前前端按后台模块拆分的交互方式。它不改变主 Spec 的范围，不替代 R2 标准本地 migration、真实集成或具名验收，也不授权代码、数据库、外部环境、提交、发布或部署变更。

## 2. 触发原因与现状判断

### 2.1 用户问题

当前需求工作台仍以列表、表单和模块导航为主要作业入口；受控作业、审批、Bridge、Skill 和审计位于单独的“作业”页面。产品经理需要先理解平台模块，再手工在需求和 Agent 能力之间切换，实际体验仍然接近传统管理后台。

### 2.2 与权威方案的偏差

主 Spec 已明确：

- 产品经理负责登记需求、维护范围和产物、发起作业、推进门禁并组织验收。
- 产品经理应从当前需求/CAP/版本直接发起 `AgentRun`。
- Agent 事件、审批、结果和证据应回到同一需求、CAP、版本和门禁。
- Web 与 Zed 围绕同一 `runId` 交接和恢复。
- AI 负责整理、分析、提出问题、生成候选、制作原型、检查一致性和汇总证据；产品经理仍对产品决策和验收负责。

当前实现具备分离的需求、产物、AgentRun、审批、Bridge、Skill 和审计页面，但没有把它们组合成产品经理的连续任务空间。因此这是交互架构偏差，不只是字体、颜色或首页布局问题。

## 4. 目标、非目标与领先性口径

### 4.1 目标

1. 产品经理从一个需求工作空间完成澄清、决策、产物、作业、审批和验收，不手工搬运上下文。
2. Agent 根据当前阶段、版本、权限和材料主动建议下一步，但只有用户确认后才能形成产品决策或受控副作用。
3. AI 输出同步呈现为可编辑、可比较、可确认的结构化草稿，而不只是消息气泡。
4. 每次执行显示 `runId`、Skill、MCP/工具、工作区、Git 基线、授权范围、进度、结果和证据。
5. 页面刷新、断线或跨 Web/Zed 后能从持久化状态恢复，不重复执行副作用。
6. 保留列表、表格、看板和治理中心，作为跨对象管理与运营视图，而不是单需求主要作业入口。

### 4.2 非目标

- 不做没有业务对象绑定的通用聊天机器人。
- 不让模型自行决定产品范围、门禁 PASS、验收或发布授权。
- 不在本轮新增外部字体、装饰性动效、营销 Hero 或大面积渐变。
- 不以 fixture、内存消息或演示记录替代标准 `pfc_local.pfc` 事实。
- 不在交互设计未确认前创建 conversation schema、API 或业务页面。
- 不把 Zed、MCP、Skill 或 Codex 的存在本身当成产品价值完成。

### 4.3 领先性分级

| 等级        | 可使用结论                     | 必要证据                                                                 |
| ----------- | ------------------------------ | ------------------------------------------------------------------------ |
| L0 概念     | “采用 AI 原生方向”             | 本基线经产品负责人确认                                                   |
| L1 样板     | “代表页面达到目标基线”         | 真实 PostgreSQL 数据、真实 AgentRun、三宽度视觉与交互验收                |
| L2 闭环     | “具备 AI 原生产品作业闭环”     | 一个真实但非生产需求完成 G0-G12，Web/Zed/Skill/MCP/审批/证据全链路通过   |
| L3 领先证据 | “在目标场景具备行业领先性证据” | 与选定标杆执行同任务的可复现实测、用户任务成功率、耗时、纠错率和治理指标 |

在达到 L3 前，禁止在交付结论或对外材料中直接声称“行业领先”。

## 5. 方案比较与选择

| 方案                      | 描述                                                   | 优点                                | 主要问题                                     | 结论     |
| ------------------------- | ------------------------------------------------------ | ----------------------------------- | -------------------------------------------- | -------- |
| A. AI 助手侧栏            | 保留现有页面，在全局增加聊天抽屉                       | 改动小                              | 上下文和结果仍需跨页面搬运，AI 是附属工具    | 不采用   |
| B. Chat-only              | 首页直接变成全屏对话，所有状态藏在消息中               | 第一感知强                          | 业务事实、版本、审批、对比和多人协作难以扫描 | 不采用   |
| C. Agent + 结构化工作空间 | Agent 对话、业务对象画布、生命周期和执行证据在同一空间 | 符合主 Spec，兼顾智能作业和企业治理 | 需要会话、对象、状态和 UI 的跨 CAP 设计      | **采用** |

方案 C 的核心约束是“双核而非双源”：Agent 是作业入口，结构化对象是事实核心。二者必须在同一页面同步，但只有后者能推进生命周期状态。

## 6. 产品信息架构

### 6.1 目标一级导航

一级导航按用户任务组织，不按后端模块组织：

| 一级入口     | 用户问题                         | 主要内容                                               |
| ------------ | -------------------------------- | ------------------------------------------------------ |
| `我的工作台` | 现在最需要我处理什么？           | 待决策、待审批、阻断、运行中任务、Agent 简报和继续作业 |
| `产品空间`   | 这个产品和需求的权威事实是什么？ | 需求、CAP/POD、材料、产物版本、门禁、决策和追踪        |
| `交付中心`   | 当前版本如何实现、验证和发布？   | AgentRun、代码/文档变更、测试、验收、发布、观察和复盘  |
| `治理中心`   | 哪些人、工具和动作被允许？       | 团队、角色、工作区、Bridge、Skill、MCP、授权和审计     |

全局区域只保留品牌、一级导航、全局搜索/命令入口、唯一上下文主操作和账户。当前能力尚未真实可用时，对应入口不得制造假内容；应隐藏或明确显示不可用原因。

### 6.2 对现有导航的迁移关系

| 现有入口               | 目标位置                                       |
| ---------------------- | ---------------------------------------------- |
| 需求管理               | 产品空间 / 需求组合视图                        |
| 门禁中心               | 产品空间 / 生命周期与门禁                      |
| 材料库                 | 产品空间 / 来源与材料                          |
| 作业                   | 单需求工作空间内联；跨需求运行进入交付中心     |
| 审批                   | 我的工作台待办；详情内联；全量记录进入治理中心 |
| Bridge / Skills / 审计 | 治理中心                                       |
| 团队空间               | 治理中心 / 团队与权限                          |

## 7. 代表性页面：需求 Agent 工作空间

### 7.1 页面任务

代表性页面不是新的首页展示，而是产品经理处理一条真实需求的主作业空间。入口 URL 必须绑定需求和可选会话，例如 `/requirements/:requirementId/work`；刷新和返回保留当前版本、焦点对象和筛选状态。

### 7.2 页面结构

```text
GlobalHeader
  一级导航 | 全局搜索/命令 | 当前团队 | 账户

RequirementContextHeader
  需求名称 | 阶段 G0-G12 | 当前版本 | Owner | 风险 | 唯一主操作

LifecycleRail
  当前阶段 | 已完成门禁 | 阻断 | 下一步 | 回退影响

AgentWorkspace
  ContextRail
    来源材料 | 待确认问题 | 已确认决策 | 关联产物 | 相关运行
  WorkStream
    用户意图 | Agent 计划 | 澄清问题 | 结构化建议 | 运行进度 | 结果摘要
    AgentComposer：上下文范围 | 作业类型 | 输入 | 发送/停止
  ArtifactCanvas
    当前业务对象 | 草稿/权威版本 | Diff | 来源 | 校验 | 确认动作

EvidenceBar
  runId | Skill | 工具/MCP | 工作区/Git | 授权 | 证据 | 审计
```

### 7.3 宽度适配

| 视口 | 行为                                                                                     |
| ---- | ---------------------------------------------------------------------------------------- |
| 1920 | ContextRail、WorkStream、ArtifactCanvas 三列同时显示；主工作流居中，画布拥有足够可读宽度 |
| 1440 | ContextRail 可折叠，WorkStream 与 ArtifactCanvas 双列；生命周期摘要保持一行可扫描        |
| 1280 | ContextRail 进入可恢复抽屉；WorkStream 与 ArtifactCanvas 保持双列，可一键聚焦任一侧      |

仅支持 PC Web，低于 1120px 显示现有桌面宽度提示。每个工作区只允许顶层兄弟滚动区域，不在卡片、消息或画布内部继续嵌套滚动；键盘焦点进入区域时必须保持可见。

### 7.4 对话不是纯文本流

WorkStream 允许以下一等内容块：

- `ClarificationCard`：一次最多呈现三个最高影响问题，解释为什么需要回答。
- `PlanCard`：显示 Agent 建议步骤、依赖、预期产物和需要授权的动作。
- `StructuredDraftCard`：字段级草稿，标记来源、置信边界和未决项。
- `ActionProposalCard`：写入前显示对象、版本、字段、影响范围和回退方式。
- `ApprovalCard`：审批范围、原因、有效期、批准人要求和批准/拒绝/缩小动作。
- `RunProgressCard`：排队、运行、等待输入、等待审批、验证和结果事件。
- `ResultCard`：区分 transport status 与业务 outcome，展示证据和未验证风险。
- `RecoveryCard`：断线、UNKNOWN、Bridge 离线或版本冲突时给出可执行恢复路径。

普通 Agent 文本只负责解释，不得单独改变业务对象或阶段。

## 8. 人机责任与动作模型

| 行为       | Agent 可以做                              | 必须由人确认                           |
| ---------- | ----------------------------------------- | -------------------------------------- |
| 理解输入   | 汇总材料、识别冲突、提出问题              | 业务事实是否准确、范围是否完整         |
| 产品设计   | 生成目标、方案、任务链、原型和 AC 候选    | 产品取舍、非目标、规则和交互决策       |
| 结构化写入 | 生成字段级变更建议和 Diff                 | 应用到权威对象及其作用范围             |
| 工具执行   | 在已授权范围内调用 Skill/MCP/Bridge/Codex | 新权限、高风险动作、外部动作和范围扩大 |
| 门禁与验收 | 检查证据并给出 PASS/BLOCK/WARN 候选       | 正式产品确认、测试验收、发布和业务验收 |
| 下一步     | 基于当前状态推荐最小下一动作              | 是否继续、调整、暂停或回退             |

产品经理始终是需求责任人；AgentRun 可被委派给 Agent，但不能把人类 Owner 替换为 Agent。

## 9. 状态与反馈规范

### 9.1 工作会话状态

`IDLE / PLANNING / WAITING_INPUT / PROPOSING / WAITING_CONFIRMATION / DISPATCHING / RUNNING / VERIFYING / COMPLETED / FAILED / CANCELLED / UNKNOWN / OFFLINE`

状态只由服务端权威事实和事件计算。聊天文案不得推断或覆盖状态。

### 9.2 必须可见的反馈

- 用户提交意图后 100ms 内出现本地提交反馈；服务端接收后替换为权威状态。
- 超过 300ms 的读取显示稳定尺寸 skeleton；长任务持续显示阶段、最近事件和停止入口。
- 失败提示必须包含原因、受影响范围和恢复动作，不能只显示“操作失败”。
- UNKNOWN 与 FAILED 使用不同语义；UNKNOWN 优先只读核验，不能自动重试副作用。
- 所有审批和确认显示精确对象、版本和作用域；“同意”只覆盖当前展示范围。
- 动效只表达状态变化和空间连续性，使用共享 motion token，并支持 `prefers-reduced-motion`。

## 11. 数据、接口与模块边界

### 11.1 权威事实

- `Requirement`、`Decision`、`ArtifactVersion`、`GateRun`、`AgentRun`、`Approval`、`Evidence` 继续存储在标准 PostgreSQL。
- 需要跨刷新恢复的产品会话必须有正式持久化模型；不得以 React state、浏览器内存或 fixture 作为产品事实。
- `AgentRun` 继续表示一次可执行作业；自由澄清会话不能被强行伪装成 AgentRun。

### 11.2 后续设计需要补齐的模型候选

- `ProductWorkSession`：绑定团队、需求、版本、当前阶段、当前控制端和恢复点。
- `WorkTurn`：保存用户输入、Agent 响应摘要、结构化内容引用和顺序。
- `ContextBinding`：显式绑定来源、问题、决策、产物、运行和证据。
- `ActionProposal`：保存拟议变更、目标版本、影响范围、确认状态和应用结果。

这些只是候选，不构成 schema 决策。进入开发前必须形成 contract、状态机、migration、repository、API/SSE、权限、保留期和清理设计，并取得单独确认与本地 schema-change 授权。

### 11.3 代码所有权

- `apps/web/src/work-sessions`：路由级产品作业空间、数据绑定和页面状态。
- `apps/web/src/agent-runs`：保留运行运营视图；可复用的运行详情不得复制到 work session。
- `apps/server/src/work-sessions`：HTTP/SSE 边界和应用服务装配。
- `packages/domain`：会话、建议、确认和权威状态不变量。
- `packages/contracts`：版本化 DTO、事件和错误码。
- `packages/persistence`：migration、repository、事务和 outbox。
- `packages/ui`：纯视觉 token、组件和交互模板，不保存业务状态。

`App.tsx` 只负责认证、路由和跨页装配。不得把工作空间、Agent 编排、审批或持久化逻辑继续堆入 `RequirementWorkbenchApp.tsx` 或 `AgentRunsPage.tsx`；实施时增加架构测试保护边界。

## 13. 测试与验收设计

### 13.1 代表性任务

1. 从一条已持久化需求继续作业，Agent 自动带入当前材料、版本、阶段和 Owner。
2. 回答高影响澄清问题，将 Agent 候选以字段 Diff 形式确认到需求事实。
3. 从同一页面选择固定 Skill 发起 AgentRun，观察流式进度并处理中途输入。
4. 对受控写入审批进行批准、拒绝和范围缩小，验证未授权动作不发生。
5. 审查产物版本和证据，确认、退回或保持 BLOCK。
6. 刷新、Bridge 断线、UNKNOWN 和跨 Web/Zed 后恢复同一上下文。

### 13.2 产品验收门槛

| 维度       | 候选门槛                                                           |
| ---------- | ------------------------------------------------------------------ |
| 任务连续性 | 代表任务 1-5 在一个需求工作空间完成，业务上下文手工复制次数为 0    |
| 事实一致性 | 100% 状态变化可从 PostgreSQL/API 读回；消息文本不能单独推进阶段    |
| 授权       | 100% 受限动作展示对象、版本和范围；未授权写入为 0，自批绕过为 0    |
| 可恢复     | 刷新、断线和重连后恢复同一需求/版本/runId；重复副作用为 0          |
| 可追踪     | 100% 被确认的 AI 产物可定位来源、版本、Skill/工具、Run 和确认人    |
| 可理解     | 受试者在 10 秒内能指出当前阶段、最大阻断、Owner 和下一步           |
| 视觉       | 既有 100 分视觉量表达到 90 分，任一维度不低于该维度满分的 80%      |
| PC 兼容    | 1280、1440、1920 无遮挡、断字、不可达操作或焦点丢失                |
| 可访问性   | 键盘完成主流程；焦点可见且不被 sticky/overlay 遮挡；状态不只靠颜色 |

这些门槛需由产品负责人确认后才成为正式 AC。自动测试不能替代人工视觉和任务验收。

### 13.3 工程验证候选

- TDD：先补 contract/domain/UI 失败测试，再实现最小行为。
- 架构测试：路由页面、应用服务、domain、repository 和 UI primitives 保持分层。
- isolated migration/repository integration：只使用 `codex_test_*` schema 和确定性 factory。
- API/SSE：顺序、幂等、断线恢复、权限、并发、取消和 UNKNOWN。
- Playwright：真实本地 PostgreSQL 数据；三宽度；键盘、hover、focus、loading、empty、error、offline 和 URL 恢复。
- proportional gate：开发中 quick；持久化/API 完成后 core；代表页验收候选运行 full。

## 14. 风险、降级与回滚

| 风险                     | 控制                                            | 停止/回滚触发                          |
| ------------------------ | ----------------------------------------------- | -------------------------------------- |
| Chat 掩盖权威事实        | 结构化画布和状态栏始终可见；消息只解释          | 用户无法判断版本、状态、Owner 或下一步 |
| AI 静默修改对象          | 先生成 ActionProposal/Diff，再显式确认          | 出现未确认业务写入或假 PASS            |
| 页面三列过载             | 渐进披露、可恢复折叠和单一主操作                | 1280 主任务不可完成或焦点顺序混乱      |
| 新会话模型形成第二事实源 | lifecycle 对象继续权威；会话只引用事实          | 会话与 PostgreSQL 状态无法确定谁为准   |
| 后台任务失控             | 有界并发、超时、停止、审批和事件心跳            | 无法取消、重复副作用或恢复不确定       |
| 再次偏离 POD             | ledger 路线和 CAP/Unit 不变，每次检查点回到 POD | UI 迭代开始声称替代 R2/M2 退出条件     |

功能回滚候选为关闭 AI 工作空间入口并回到现有需求详情和作业运营页；数据库 migration 一旦承载事实只允许前向修复，不 drop/cascade。回滚不得改用 fixture 冒充能力。
