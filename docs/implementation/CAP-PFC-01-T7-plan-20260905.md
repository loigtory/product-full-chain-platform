## 1. 目标与非目标

- 整合 T1～T6 的五个 Unit 和 12 条 CAP AC，补齐桌面端键盘/焦点、错误恢复、性能、安全及完整质量门禁证据。
- 把 Full gate 从“声明缺项并拒绝运行”改为真实串行执行 core、PC Playwright、权限、并发、恢复、安全、性能和依赖审计；任何一步失败均 fail closed。
- 生成可进入人工 PC 验收的候选证据和 G9-A 实现状态表，但不把工程 PASS 表述为产品验收、发布批准或业务验收。
- 不新增或升级依赖，不改变已确认业务状态机/API/数据库模型，不接入真实 CAP-PFC-02～05，不执行默认 `pfc` migration，不 commit/push/merge/发布/部署。

## 2. 已选方案与影响范围

1. 采用无新增依赖方案：复用 React、Vitest、Playwright、Node 标准库和现有测试工厂。
2. 对通用对话框、问题抽屉和人工门禁对话框统一增加 Escape 关闭、Tab 焦点约束、打开后首个有效控件聚焦和关闭后焦点恢复；保留现有视觉语义。
3. 桌面目标仍为 1280/1440/1920；低于 1120px 只显示“请使用桌面宽度”提示，不扩展为移动端验收。
4. 权限、并发、恢复门禁调用已存在的定向测试；新增静态安全脚本和确定性本地性能 smoke。脚本不得扫描或输出真实敏感值。
5. 质量 profile 分开表达“工程 Full 可运行”和“正式验收仍阻断”，不得通过删除验收、联调、观察或发布条件制造绿色结论。

涉及路径：`apps/web`、`packages/test-data`、`tests/unit`、`tests/e2e`、`tests/performance`、`scripts`、`package.json`、`.quality-gate/profile.json`、本地证据文档。

## 4. 验证与退出条件

- TDD 顺序：先确认键盘/焦点测试因缺少行为失败，再实现最小 UI 加固；安全与性能脚本各自先验证失败语义，再接入 Full gate。
- Quick、Core、Full 和三种 PC viewport Playwright 必须实际执行；dry-run 仅证明计划，不是 PASS。
- Full 技术 PASS 的最低条件：权限、并发、恢复、安全、性能、PC E2E、依赖审计均真实通过，且没有残留 Vite/Playwright/test runner。
- 代码评审、测试和安全责任人均已登记为陈立，人员数量或独立性不构成 G9-A 阻断；正式接受仍必须有对应证据结论。
- PFC-02/04 真实联调、G10 产品验收、G11 发布、G12 业务验收和建议的一个工作日隔离观察均不在 T7 本地授权内，持续 BLOCKED/待后续授权。

## 5. 风险、回滚与停止条件

- 风险：焦点陷阱造成不可操作、性能测试因构造方式失真、安全脚本误报、Full gate 重复执行导致资源压力、技术 PASS 被误解为发布就绪。
- 控制：只约束已打开浮层；预算明确为本地工程 smoke；安全规则使用定向检查；门禁串行单 worker；报告分列技术与生命周期结论。
- 回滚仅反向编辑未提交 T7 文件；不删除默认 schema、用户数据或本地 PostgreSQL 服务。
- 停止条件：需要修改已确认业务语义、需要真实数据/凭据/外部环境写入、需要依赖变更，或发现越权正文、凭据泄露、重复推进或资源异常。
- 本轮不使用并行代理；所有命令串行。结束时审计 3001/5173 和测试 runner，报告保留进程的 PID/端口/用途/停止方式。
