## 一、目标、现状与方案选择

目标是：在 PG 模式下，通过现有工作台创建需求、回答问题、保存和确认版本、登记材料、发送消息、审批和执行模拟作业；关闭服务和浏览器后重新打开，能从数据库和本地文件恢复原内容。接口返回成功必须意味着本轮业务事实已提交；网络失败、旧版本冲突与未知执行结果必须可见。

## 二、本轮闭环和延期边界

按一个 M2c-2 交付范围、串行四个检查点实现，避免需求持久化而作业仍偷偷写内存：

1. 仓储与事务：补表、DTO、编号、去重、事件、权限和应用启动；先 API/SQL 验证。
2. 需求工作区：新建、问题、版本、材料原文件、消息/引用/Diff，接原版 UI 并验证刷新。
3. 执行闭环：计划、运行、行/回放/质量门、租约、通知与 WS 提交后推送；验证重启、取消与并发。
4. 全部回归、独立读回、文件/数据库故障、三档 PC 截图、自审与陈立验收。其间不将半完成 PG 模式作为日常入口。

全部 M2c-2 基础能力做完才交付；四个检查点不重新定义 25 号总路线，也不是默认授权四个新的独立版本。

以下边界需与本方案一起确认，不能被演示数据掩盖：

| 能力 | M2c-2 的处理 | 后续归属 |
| --- | --- | --- |

## 三、数据、迁移与运行方式

### 明确两类环境

- **实施验证目标，拟申请本轮授权**：仅 loopback PostgreSQL 18、`pfc_local`、`pfc_app_local`，新增领域测试唯一 schema `codex_test_m2c_20260912_domain`；旧 M2c-1 回归另用其原 schema，见第八节。新增工厂临时文件根固定为 `.local/m2c-2-domain-20260912/files/`，每次测试子目录带 runId/attempt 且必须不存在。如果跨日，先在 28 号明确新的单一 runId/schema/目录，不能扩为任意前缀批量清理。每次创建前必须不存在，最多 2,000 行合成数据、100 MiB 合成文件；所有数据带 `CODEx_TEST_M2C_20260912_domain` 标记。扩大到 2,000 行是为了行流/事件重放和分页测试，相对 M2c-1 的 200 行是待确认的明确变化。
- **后续日常数据目标，当前只确认设计**：`pfc_local.pfc_workbench`，文件区 `.local/pfc-workbench-files/`，配置来自忽略文件。先生成完整版本迁移、目录/表所有权检查、备份和回退说明，隔离全链路通过后提交启用清单。当前“确认实施”不执行该持久 schema 的 DDL/DML，也不自动保留测试实例当正式服务。

业务数据选择建议为**空库起步**。只由显式初始化命令建立配置所指定的单租户身份元数据；应用启动和浏览器打开都不能创建演示需求、材料、消息、知识或 run。旧 localStorage、旧 app_state、`pfc` 与历史备份原位保留。需要导入时另做预览、字段映射、冲突处理与确认，不在本轮自动转换。

连接模式采用 `PFC_DB=memory|pg`：默认 memory 可延续演示；`auto` 在 PG 接入后不再作为自动选择和降级开关，返回明确配置错误。PG 需要目标、租户、私有登录配置与密钥全部就绪。启动仅校验迁移版本/checksum/表和必要列约束；迁移由 CLI 显式运行。运行中失联返回 503 `STORAGE_UNAVAILABLE`，连接与 SQL 超时分别 3 秒；有成功提交但 HTTP 响应丢失的情况，通过 commandId 查询/重试确定结果，不能承诺“任何超时都未写入”。

001 SQL 和已入库 checksum 保持不可变。在版本注册中新增 `002-domain-workspace.sql`，增加缺失字段与本轮表；迁移支持“指定目标版本”，原 M2c-1 测试仍只迁到 001，新专项到 002。不得用删掉旧版本记录、重写 001 或一次运行旧 m1-schema.sql 的方式升级。

## 四、事务、事件与恢复规则

1. **每条命令先做身份、范围和版本校验**。需求创建连同 idea v1、两条问题、原始想法文本材料、审计和事件一起提交；回答问题连同对应 idea 新版本一起提交。它们是用户输入及未确认模板，不是导入演示历史。
   首次推进到 req/design/dev 时，同一事务建立该阶段的未确认模板版本，模板只使用已存在的输入/确认内容并明确“待补充/待确认”；不提前生成后续已完成产物。PG 未接入的 test/accept/release/observe 写入返回能力未就绪，不靠模板跳过质量/验收门。服务器分配新版本号，不能信任客户端用旧号覆盖。
2. 保存版本/采纳 Diff 必须携带基线版本及 revision；落库前锁定需求聚合，旧基线返回 409，保留用户编辑供比较。确认要求当前阶段最新、未失效版本；下游失效按阶段顺序处理，不能沿用 service.js 中“不同阶段版本号大小”比较。该修正和服务端问题/材料阻塞校验是本轮明确的契约差异。
3. 材料替换增加版本并记录影响；纳入/排除由服务器决定，不能信任客户端仅改 allowed。材料/版本失效之后，未启动作业原计划失效；批准与 start 均核对计划基线，旧基线返回 409，不发执行。运行中只记录影响，不偷偷撤销已经产生的外部结果。
4. 命令去重跨进程保存。相同 key 和请求指纹返回既有结果，key 相同但内容不同返回 409 `COMMAND_CONFLICT`。请求结果、审计、通知和事件不能各提交一半。幂等保留至少覆盖本轮运行历史；未设计清理前不自动删除收据。
5. Web 事件在业务提交后才推送；数据库事务中写 domain_events，提交后有界发送。断线/进程崩溃后可重复投递，前端按 eventId/seq/revision 去重并用领域 GET 校正。数据库是事实，不能用已发送 WS 代替提交证据。
6. Bridge 派发保存 dispatchId 和派发状态。数据库提交前不发 job.start；发送结果不确定或服务重启时处于 dispatching/running/cancelling 的记录转 UNKNOWN，并将旧租约标 lost。**未知状态不自动重发 job.start，不自动判成功**；verify 保持读回核验性质。无需在本轮引入真实执行恢复协议。
7. PG 路径只接本轮受控模拟 Bridge；Bridge 输出事件增加 eventId/seq/dispatchId，重复或越序事件经校验去重，错误 Bridge/其他租户/旧 dispatch 拒绝。取消后到达的 done/line 不得把 CANCELLED 改成 SUCCEEDED。模拟协议扩展需同步 sim-bridge 和测试；不放行任意真实终端。
8. 进程持有的 socket、心跳和临时发送队列仍可在内存；业务状态、编号和去重结果必须在 PG。单进程池最大 2；事件每批最多 50、待发缓存最多 1,000，超限/慢客户端断开后从数据库恢复；行流初始展示最近 200 条，分页上限 200。保留现有 16,000 字符单行上限，事件负载限定 64 KiB；超过上限显式拒绝，不无界缓存。

事件恢复采用现有进程内调度和 pg，不新增 Kafka/Redis、服务、框架或依赖。以上吞吐限额是拟议保护值，必须在本轮有界压测中验证，不是容量承诺。

## 五、前端、文件与最低权限

### 一份业务事实与原型兼容

- PG 启动先读取 `/api/health` 的 storage/能力声明，失败时保留错误页，不自动 seed、切回 local 或上传浏览器旧树。空库显示空列表与新建入口。
- PG 下 `/api/state` GET 只给出存储模式/空初始化信息，PUT/DELETE 及 `/api/batch` 业务写统一拒绝 `DOMAIN_WRITE_REQUIRED`。旧客户端收到错误不能提示同步成功。memory 路径继续既有快照回归；local/mock 使用各自原存储。
- PG 的 P.save 只保存本机视图偏好和未提交草稿；不得保存一份能恢复为业务权威的 reqs/runs 树。偏好按 API 基址、身份、需求区分；退出登录清掉 token 和用户缓存。
- 新 `domain-view.js` 将领域 DTO 映射为现有渲染结构；空数组/未生成状态用于布局，不能调用 P.makeRequirement 把演示材料、已完成测试或后续版本当成已落库记录。草稿、确认信息、问题、材料、消息、行流、通知分批独立读回，加载过期响应不能写进另一个需求。
- 同步失败保留用户输入，按钮显示提交中/可重试；仅服务端成功后更新权威状态。已知提交命令保留 commandId，用户主动重发消息创建新的关联消息 ID，两者不能混淆。
- PG 中治理/发布/测试验收等未接入口按能力声明禁用并说明原因；同一 URL 不混用 PG 需求和演示治理事实。不得让旧 action 或直接调用 API 绕过该边界。

### 文件原件和消息

保留原型的单文件 10 MiB、单消息 20 份/合计 50 MiB、文本预览 200,000 字节边界。上传逐个进行，并发上限 2；服务端独立检查类型、解码后大小、需求归属、配额与 hash。租户容量由明确配置提供，不读取原型示意预算冒充真实配额。

在不引新依赖的前提下，建议沿用材料 JSON 入口，增加可选 `file:{name,mimeType,encoding:'base64',content}`，该路由 body 上限 16 MiB，普通业务路由上限 1 MiB。先落同卷临时文件并计算 SHA-256，再原子改名，最后提交 READY 元数据；响应只在文件与元数据一致后成功。不能声称文件系统与 PG 是一个事务：失败产生的孤立文件只能按本轮创建标记、无引用和精确目录核验后回收；崩溃后的孤儿先报告，禁止全目录清理。

路径由服务器按 tenant/hash 构造，拒绝请求里的绝对路径和目录穿越；不使用 express.static 暴露文件根。下载根据当前身份、req/material/version 关联授权，返回原件并可独立校验 hash。只登记/受限材料可以由有权用户保存和下载，但不能进入消息分析引用。随消息附件与长期材料共享文件存储、用途不同，不能自动把随消息上传加入长期分析上下文。

PG 对话由服务器保存用户消息与确定性的模拟回复，逐步输出也使用持久状态；停止/重发、回复引用、建议与 Diff 的采纳/拒绝留痕。重新打开页面恢复已输出内容，正在生成的模拟回复在异常重启后标为中断，不能伪造已完成。二进制文件不生成合成“解析结果”当事实；文本/图片预览与原件保存分别标识。

attachments.js 当前提示中的“对象存储”与既定无 OSS 边界不一致；实施仅在当前上传说明中改为服务端本地文件保存，并分别说明 local/mock 与 PG 的真实能力，不引入对象存储服务。
