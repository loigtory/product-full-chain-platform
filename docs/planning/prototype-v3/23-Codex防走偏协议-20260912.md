# 23 · Codex 防走偏协议（每轮会话强制执行）

> 定位：所有后续 Codex 开发会话的**行为契约**。在 19 号路线图、20 号任务模板、21 号检查点之上，规定每轮"开局怎么读、范围怎么锁、提交怎么留痕、验收怎么判"。配合 git 版本管理（基线 `69ec9eb`，main 主干 + feature 分支）。
> 适用范围：POD-PFC-001 主线后续开发（M2b-2 收尾 → M2c → M3 → M4）。文档路径 `docs/planning/prototype-v3/`。

---

## 一、为什么需要本协议

Codex 的"主动性"是最大走偏源：不读规则直接开发、顺手扩展接口/技术栈、声称完成但不跑验证、改动不留痕导致下轮对不上。本协议把**入口、范围、验收、留痕**四件事固化，每轮 Codex 先读规则再动手，交付必须带验证证据。

## 二、六条协议

### 1. 固定开局（每轮第一指令，原样粘贴）

```
先读 AGENTS.md 的 Active Handoff Scope 段 和 docs/planning/prototype-v3/README.md；

未读完不得修改任何文件；每轮任务参数见 20 号模板填写表。
```

Codex 默认读取仓库 AGENTS.md——交接范围已写入，这是最强杠杆。

### 2. 范围锁（每轮任务必须显式声明）

| 项 | 填写 |
|---|---|
| 本轮允许动 | {目录/文件白名单} |
| 禁止清单 | 不引新依赖 · 不改 12/13 号已定契约 · 不碰 `archive/` `apps/` `packages/` · 不顺手修无关 bug · 不新建架构 |
| 退出边界 | {本轮明确不做的事} |

超出白名单的改动 = 走偏，评审时直接驳回。

### 3. 基线提交与分支纪律（git 已就绪）

- 初始基线：`69ec9eb`（1817 文件，2026-09-12）；每轮先 fetch，核对最新 `origin/main` 与工作区，不能把初始提交当作当前远程头。
- 每轮开发在 feature 分支：`git checkout -b feat/{任务代号}`（如 `feat/m2c-governance`）。
- **开工一次提交**（分支起点 = main 最新）、**收工一次提交**（含代码 + 文档 + 验证证据引用）。
- 合并回 `main` 前必须通过第 4 条验收闸；合并用 `--no-ff` 保留轮次边界。
- 回退依据 = git 提交历史（不再依赖 .local 快照；`.local/` 与 `output/playwright/` 不入库，本地保留）。

### 5. 差异评审（人工验收前置）

每轮交付顺序固定：
1. **改动清单**（新增/修改/删除文件 + 行数级说明）
2. **与 19/20/21 号交接包的差异**（多做了什么、少做了什么、为什么）
3. 验证输出 + 截图证据
4. **待确认事项**（未确认的接口/范围变更单独列出，等用户答复）

用户（产品负责人）评审确认后，该轮才算验收。呼应 21 号"最终人工视觉与业务验收仍需产品负责人评审"。

### 6. 文档续编（每轮必须）

每轮续编号文档（`2x-{主题}-{日期}.md`），固定结构：

```markdown
# {N} · {主题}
## 本轮改动（文件级清单）
## 验证结果（命令 + 输出摘要 + 证据路径）
## 与交接包的差异（超范围项必须列出）
## 诚实边界（模拟/未做/待确认）

```

文档不更新 = 该轮未闭环。

## 三、每轮开工/收工 Checklist（可直接执行）

**开工**：
1. 先读固定开局资料并检查 `git status --short --branch`。逐条执行 `git fetch origin main`，核对最新 `origin/main`；工作区有他人改动时保留，不覆盖。
2. `git switch -c feat/{任务代号} origin/main`（新任务从最新远程 main 起点创建；分支已存在则先核对，不覆盖）。
3. 粘贴"固定开局"指令，等 Codex 报告已读文档清单
4. 核对 20 号填写表参数（本轮任务/白名单/禁止清单/验收命令/续编文档号），写入本轮范围记录并做开工提交。

**收工**：
1. 六条回归 + 21 号专项全绿（截图/JSON 存档）
2. 改动清单 + 差异报告 + 待确认事项
3. 续编 `2x` 号文档
4. 使用 `git add -- <逐项白名单文件>`，再逐条运行 `git diff --cached --name-status`、`git diff --cached --check`、`git commit -m "{任务代号}: {一句话}（验证：verify-* 全绿）"`、`git push -u origin feat/{任务代号}`。每条检查退出码，失败即停止。禁止全量 `git add -A` 或串接 Shell 命令；开工提交也采用白名单暂存，提交信息不得预先声称测试通过。
5. 用户在 GitHub/评审后确认 → 合并 `main`（--no-ff）

## 四、红线（一票否决）

- 引入新依赖/新技术栈/新架构而未在 20 号填写表声明 → 驳回
- 声称完成但缺少第 4 条任一项验证输出 → 视为未完成
- 修改 `archive/` 归档内容或 `apps/`、`packages/` 前期工程 → 驳回
- 编造数据/结论（零脑补）或未标注模拟边界 → 驳回
- 跳过文档续编直接交付 → 驳回
