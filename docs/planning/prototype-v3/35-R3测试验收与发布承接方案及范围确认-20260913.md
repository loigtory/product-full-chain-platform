## 3. 同一工作台的连续交互

1. **提前准备：** 关联原型/PRD/验收项被采纳后，即使业务/设计尚未确认，也能在想法/需求阶段“准备测试”。复制验收项形成待完善用例，提示缺失边界、数据和预期；不声称 AI 已覆盖全部异常或执行测试。
2. **持续补齐：** 在需求/设计/开发阶段保存草稿，上游改变时显示增删改差异，复用稳定用例文字；旧 PASS 不自动带入新基线。明确选择完整套件作为本次交付依据。
3. **提测即交接：** “登记交付并进入测试”复用关联组、确认、开发版本、项目和套件，只补交付对象与证据；一次事务冻结基线并进入 test。
4. **结果与缺陷联动：** 单项或批量登记，失败项生成待确认缺陷草稿，带入验收项/用例/实际结果/证据。修复声明后回开发准备新交付，重新测试才能关闭。
5. **测试直接承接验收：** 当前基线全部必测项通过、无未关缺陷、证据有效，“完成测试并进入验收”冻结报告；Owner 直接查看，无须重复粘贴。
6. **验收承接发布准备：** 通过进入只读发布准备，驳回带原因回开发；发布执行仍不可用。

沿用三栏、聊天、附件、上下文与现有样式。失败保留草稿并定位错误；409/503/写后读回失败支持恢复，重试复用 commandId。跨需求、成员切换及晚到响应不得串入当前需求。test/accept/release 支持已有报告版本与附件引用；本轮不新增独立用例/缺陷聊天引用类型。

## 4. 待确认的规则

### D1 · 结果来源

首个来源仅为 **USER_REPORTED（具名人工登记）**，记录登记人、实际执行时间、环境、交付对象、实际结果、附件版本及服务端登记时间。提交号/构建号是用户声明，不能标记为 Git/CI 已核验；接口拒绝客户端伪造 AI_EXECUTED/CI_VERIFIED 等来源，不执行 JSON/HTML 或外部 URL。

每条必测 PASS/FAIL 要实际结果及至少一份当前可读、归属本需求的受控附件版本。NOT_RUN/BLOCKED 要原因且不能放行。所有套件用例必测；无“一键全通过”、未测豁免或缺陷带病通过。人工测试可支撑本版产品验收，界面/报告明确其来源与具名责任；不能写成平台已执行。自动化验证所造人工记录全为合成数据，不能作为真实业务验收。

### D2 · 套件版本

整体追加套件版本，用例包含稳定 caseId、acIds、ruleIds、标题、场景、前置条件、步骤、预期、数据策略、执行方式及负责人。允许 INCOMPLETE 草稿；READY 必须覆盖当前关联组全部验收项、引用合法、ID 不重复。初稿仅复制 AC 并标记“待补边界”。

保存草稿不替换当前有效套件、不影响现有交付。显式 `adopt` READY 版本才改当前指针并检查影响；再次采用需预期当前套件及关联组，过期返回 409。比较按稳定 ID/内容摘要呈现，保留草稿文字，绝不复制旧结果到新基线。

### D3 · 交付与批次

提测要求当前业务/设计确认有效，最新开发版本有实质交付内容，当前 READY 套件覆盖全部 AC，项目/成员/材料有效，无 RUNNING/CANCELLING/UNKNOWN 作业；空模板或“待补充”不满足条件。

交付对象包括项目、版本/构建引用、变更摘要、实施/回滚说明、未实现范围声明及证据。可以手工交接；可选 Run 必须同需求且 v2 输入与当前组/确认一致，仍保留模拟属性。事务内完成成员/需求锁、revision、冻结基线、确认选定开发版本、当前交付指针、推进 test、审计/事件/幂等回执。

批次冻结交付、套件、环境、来源，状态 OPEN/COMPLETED/CANCELLED。结果只追加，每用例显式序号与前结果校验；同批次补未完成项或追加复测，不覆盖历史。已结束批次不可追加，须新建。只有当前基线/批次所有必测最新结果 PASS、证据有效且无未关闭缺陷，才能冻结测试报告、一次推进 accept。

### D4 · 缺陷与产品验收

缺陷从失败结果登记，关联稳定用例/验收项。OPEN → RESOLVED → CLOSED；RESOLVED 为具名修复声明，不是回归通过。登记修复说明及开发变更时回 dev 准备新交付；新交付必须引用新的开发版本，即使需求未变。新基线同用例 PASS 才关闭，失败 REOPEN，事件追加。上游换组时未关闭缺陷继续阻断，不能从新列表隐去。

产品验收独立于 R2 业务/设计确认。当前 Owner 冻结关联组、业务/设计确认、开发/交付/套件/测试版本、证据与验收人；确认功能验收项、权限/异常、版本/证据三项检查，并填结论/风险（可明确“无”）。ACCEPTED 追加记录并生成只读报告、进入 release 准备；REJECTED 追加原因回 dev，历史测试不删除。不支持条件通过或豁免。

已完成批次发现新失败，另建批次；已验收后登记新缺陷或新的有效测试结果，旧验收不再是当前放行依据。历史批次、报告与验收始终可追溯。

### D5 · 权限、事务与回流

Owner/Executor 可维护套件、提测、结果/缺陷、完成测试；产品验收通过/驳回仅 Owner；Viewer 只读，停用成员拒绝。membership-policy 为产品验收加 Owner 规则，commands 在 005 读取幂等回执前执行，防止降为 Executor 后重放旧成功回执。

锁顺序为成员 → 需求 → 套件/交付/批次/缺陷；命令摘要包含 URL 目标和载荷，同 ID 同载荷回原结果，换目标/载荷冲突。有效性比较业务指纹，不因无关聊天 revision 作废。已撤权登记者的结果保留历史但不满足当前出口，需当前有权成员重新登记。

| 变化                                          | 处理                                                     |
| --------------------------------------------- | -------------------------------------------------------- |
| 业务关联组、想法/业务问题、被引用材料变化     | 沿 R2 回 req，下游旧基线保留但失效                       |
| 设计方案/确认变化                             | 回 design，下游旧基线不放行                              |
| 开发版本、显式采用的 READY 套件、交付对象变化 | 回 dev，重新提测；未采用草稿不触发                       |
| 验收后新缺陷或新有效结果                      | 回 dev，旧验收仅历史，重新交接/测试/验收                 |
| 证据撤权、缺失、摘要错误                      | 阻断读取使用、完成测试、验收和发布输入就绪，定位具体证据 |
| 未引用新附件、聊天、历史查询                  | 不污染业务基线                                           |

新阶段也能提出/采纳业务修改，保留 R2 活动作业阻断。通用 save/confirm/review/diff 不得修改派生测试/验收报告；通用 advance 不绕开新服务。真实发布后的变更锁由 M2c-4 设计。

### D6 · 数据与 API

新增显式 `005-testing-acceptance.sql`，001–004 原文件/校验和不变。九张新表为 test_suites、test_cases、delivery_baselines、test_batches、test_results、defects、defect_events、product_acceptances、verification_refs。reqs 加当前套件/交付指针，草稿不占有效指针。外键覆盖租户/需求/父版本组合；用例/批次必须属于同套件，交付/套件同组，AC 引用写入时验证并冻结。

### D7 · 容量、恢复与兼容

- 每套件 200 用例，每例 40 步，单文本 4000 字符，JSON 写入 512 KiB；服务端字段级错误。
- 每批次 200 用例、每次登记 100 项、每例历史 100 条、每批总结果 2000 条，触顶新批次，历史保留。
- 单项证据 20 附件/合计 50 MiB；沿用单文件 10 MiB、文件根 100 MiB，不新增外部存储。
- 每需求最多 5 个 OPEN 批次；分页默认 20、最大 100、offset 上限 10000，摘要 512 KiB；导出受约束 JSON，不扩 CSV/可执行 HTML。
- 池上限 2、连接/语句 3 秒、空闲事务 5 秒；无后台自动测试/AI轮询。新请求 12 秒，旧回归保留有界超时，套件外层 300 秒。
- 写后读回失败保持“已提交待核实”，同 commandId 恢复；服务端拒绝保留未提交草稿，刷新/切需求恢复有边界。
- PC Edge 1280/1440/1920 验证主流程、键盘、焦点、错误、附件和聊天手势；移动端/新浏览器认证不在本版。只测本地容量冒烟，真实吞吐与工具/模型费用尚未测量。
