# 路线图：从原版工作台交互到真实产品闭环

版本：V0.2 草案，2026-09-11。Parent POD：`POD-PFC-001`；权威产品版本仍为 V0.1，5 CAP / 26 Unit。当前台账里程碑为 M2。本方案不替换台账，不授权恢复实现。

原型基线按最新用户选择调整为原版 `index.html`。P1 代表页和 P2 执行接入保留原版完整交互，尤其是对话卡片、Zed 对话流和右侧终端/画布/证据。原版现已补齐代表性状态，逐项见开发交接，不以 V3 替换页面；P0–P4 依赖顺序与 CAP/Unit 范围不变。

最新交付：[原版开发交接](05-原版开发交接.md) 已提供可走查流程和 26 Unit 的页面/动作/接入映射。原型完成不增加下表的集成计数，工程先继续 P0。

## 1. 交付顺序

建议采用 P0–P4 五段推进。P 是本方案的工作顺序标记，**不是新产品版本或新 POD 里程碑**；M1–M3 的原范围和退出条件继续有效。

```mermaid
flowchart LR
  P0["P0 统一基线<br/>源码、迁移、范围与路线"] --> P1["P1 真实工作台<br/>需求、文档、确认"]
  P1 --> P2["P2 受控 AI 闭环<br/>执行、能力、恢复、证据"]
  P2 --> P3["P3 完整交付链<br/>测试、验收、发布观察、Zed"]
  P3 --> P4["P4 团队试点<br/>部署、协作、观测、验收"]
```

下一段实现的首个可评审结果应是：**同一条标准数据库需求，在原版风格的工作区里完成问题回答、文档新版本、版本比较与确认，并从证据侧栏独立读回。**这个样板直接承接当前 M2-R3 产物协作任务；必须说明其对 R3 验收的作用，不能另开长期 UI 迭代替代 POD 路线。

## 2. P0：统一原型、范围、源码与证据基线

目标：让后续计划从准确工程状态出发。

| 工作                   | 交付物                                                          | 退出条件                                        |
| ---------------------- | --------------------------------------------------------------- | ----------------------------------------------- |
| 确认原版交互的产品规则 | 八阶段投影、取消/关联重试、能力生效范围、团队部署顺序的决策记录 | 影响首个样板的决定有明确口径                    |
| 校准工程状态           | 当前源码快照、迁移清单、标准库只读结果、运行依赖清单            | 区分源码存在、隔离验证、标准集成与验收          |
| 收口记录差异           | R3a/R3b 证据核对，POD 单一路由与检查点一致                      | 不凭检查点文字直接提升 Unit 状态                |
| 修复已有入口阻断       | MCP 请求版本字段及相关测试一致                                  | `check:types` 通过，受影响回归及适用 Quick 通过 |
| 完成代表页设计准备     | 原型页面/状态研究、UI 变量映射、对象与 API 接入清单             | 方案确认；先迁移一个真实页面的范围明确          |

依赖：标准库只读可达；涉及标准 schema 变更时另有明确本地授权。旧记录称 008/009 未应用，本次没有替代现场读回。

P0 不新增业务能力，也不能用修好编译来宣称 M2 完成。当前用户仍要求暂停平台迭代；本轮只交付 P0 的核对建议与已执行的只读检查，代码修复留给确认后的实施。

## 3. P1：需求与产物真实工作台

目标：在标准 PostgreSQL 上交付第一个连续工作空间，同时收口 M1 基础验收和 R3a 的核心产物体验。

范围：

- 首页待办、需求清单、创建需求、材料登记、问题回答与确认、当前门禁及上下文恢复。
- 原版代表页：左侧上下文、中央讨论/结构化动作、右侧正文/差异/评审证据；保留旧深链接。
- 产物目录、正文归档、新版本、已确认版本派生草稿、版本级评审。
- 历史/未来阶段只读；明确动作前置条件；空、加载、失败、无权限、版本冲突可处理。
- 使用已有团队、角色和工作区事实；已有 AI 依赖可用时接入，缺失时明确显示不可用，不生成演示成功。

主要依赖：CAP-01、CAP-02-01/03/04、CAP-04-01/02/03，migration 008 及既有会话依赖。正式 schema 应用须在隔离验证和范围确认后进行。

退出标准：

1. 不依靠固定示例，创建一条合成验收需求并完成登记、回答、文档修改与确认。
2. 数据库/API/UI 的需求、基线、版本、哈希和确认人一致；刷新与切换不串记录。
3. 并发修改不会覆盖旧内容；原版本与确认历史保留；无证据时不显示门禁通过。
4. 代表页在 1280 / 1440 / 1920 完成浏览器与用户视觉确认，再复用到其余入口。
5. Quick/Core 及命中的恢复、权限、浏览器检查通过；M1 的具名结论与既有观察要求逐项关闭，不仅统计 9 个 Unit 的集成标记。

P1 可交付真实的需求与产物作业，不承诺完整代码 Agent、发布或生产能力。

## 4. P2：AI 作业、能力治理与证据闭环

目标：收口 M2 所需的 11 个 Unit，并让对话、执行、审批、结果和证据回到同一业务上下文。

范围：

- 真实 ProductWorkTurn、类型化 ActionProposal 与业务服务应用结果。
- 现有 AgentRun 检查/受控编辑的标准集成，取消、核验、关联重试与断线恢复。
- R3b 的已登记只读 MCP 能力、运行时快照、调用结果、产物版本和证据归档。
- 团队能力目录、阶段默认策略、会话临时选择和执行时快照；不自动安装外部能力。
- Requirement/CAP/Unit/AC/ArtifactVersion/AgentRun/Evidence 的双向追踪。
- Bridge 配对、离线、撤销与审计；完善开发/测试所需的 Shell、文件与 Git 工具链，在同一对话返回命令结果。代码/测试任务若超出现有 operation，在对应 CAP 的确认设计中扩展，明确预览进程的启动、状态与停止。Shell 可在授权任务内使用，不为每条命令单独设置产品按钮或重复人工确认。

关键依赖：P1 的版本事实；R3 的 MCP 版本字段修复；migration 009；确实存在且经复核的本地只读 MCP。缺少可用 MCP 时，该真实集成项保持阻断，不以 mock 关闭。

退出标准：

1. 一个真实回合生成建议、明确确认并应用，准确产物版本与证据可独立读回。
2. 本地 Shell/文件/Git 执行在批准范围内连续工作，返回输出、退出码与相关文件差异；越权目录、过期授权和被撤销 Bridge 被拒绝。命令超时/取消和进程清理有证据；保留的预览可查看状态并停止。
3. 取消确认前不显示已取消；未知结果需核验；重试不重复副作用，旧 run 记录保留。
4. 一个经复核的只读 MCP 调用有登记、运行时匹配、请求、结果和脱敏归档证据。
5. 全局/团队策略、阶段绑定和会话选择生效范围正确；既有执行快照不被配置更新覆盖。
6. R3a/R3b/R3c 的适用证据汇总，M2 11/11 按标准环境验证；Full、角色验收及标准库读回分别完成。

若能力配置无法由既有 Unit 的确认范围承载，先回到对应 CAP 设计；若改变 CAP/Unit 或估算边界，再回到 G3–G5。不能以“原型已有按钮”跳过此判断。

## 5. P3：测试、验收、发布观察与 Zed 交接

目标：实现 M3 的 6 个 Unit，形成完整的非生产试点证据链。

| 工作包         | 具体交付                                                 | 核心验收                                                 |
| -------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| 提测与测试     | 测试计划、AC 映射、数据政策、执行结果和缺陷回流          | 实现/Spec/测试版本一致；失败和未测范围可见               |
| 产品验收       | 验收清单、负责人结论、残余风险                           | 勾选操作有准确版本与结果依据；测试通过不自动代表验收通过 |
| 发布准备       | 已验收版本、目标、配置依赖、回滚、观察窗口和范围审批     | 授权准确；拒绝、过期或版本漂移时不执行                   |
| 发布与观察     | 有界非生产发布演练、真实执行结果、失败/回滚与观测记录    | 审批与执行分离；没有指标时显示缺口；不把演练计作生产上线 |
| 最终验收与复盘 | 目标/实际结果、业务责任人结论、遗留项、Owner、后续安排   | G12 有实际来源；上线不替代业务最终验收                   |
| Web/Zed        | 同一 runId、仓库/文件/差异定位、单一交互控制端与接管记录 | 双端不并发驱动同一作业；恢复与输入控制经过验证           |

依赖：P2 的版本、追踪、执行、授权和证据。CAP-05 先确认产品规则与模型，再设计迁移/API/UI；当前不能只扩展首页卡片便算实现。

退出标准：M3 6/6 具备同版本技术集成证据；至少一个真实、明确非生产目标的需求形成 G0–G12 试点证据包。测试数据有隔离和清理，演练记录标明目标与授权，未证明的真实外部效果保持未验证。

P3 证明端到端技术链路，最终团队试点与整体验收在 P4 关闭。

## 6. P4：团队试点、部署和整体接受

目标：将本地验证的能力交给已确认范围的团队试用，完成 V0.1 的整体退出。

范围：

- 保留应用内管理员邀请账号的原首期选择，不新增 SSO；验证角色分工、多用户并发和跨团队不可见。
- 完成平台入口、TLS/WSS、Bridge 设备信任、凭据生命周期与远程连接设计。现有 loopback 限制不是远程部署配置模板。
- 明确部署目标、Owner、构建来源、配置与迁移、备份恢复、回滚及烟测；获得对应部署授权后执行。
- 以已确认容量假设为试点上限：不超过 10 用户、5 Bridge、每 Bridge 最多 3 个并行 AgentRun；先小范围观察再扩展，实际负载与可用人数重新登记。
- 观察任务成功率、操作耗时、版本冲突、UNKNOWN、取消与归档积压，记录问题和后续决策。

退出标准：

1. 5 CAP / 26 Unit 的范围、集成证据和具名验收一致；M1/M2 遗留验收与观察项全部清理或有本次明确接受的残余风险。
2. 一个团队在实际使用路径中完成端到端试点，跨角色权限、版本和运行恢复正确。
3. 发布候选的 Full、安装/升级/回滚与烟测通过；目标环境、版本和证据可定位。
4. 约定观察窗口有实际监控与结论；业务责任人决定继续、调整或暂停。

发布到 PFC 的团队环境，与 PFC 代用户执行下游业务系统的生产发布是两类动作。后者仍需要准确目标和动作授权，不随平台部署自动开启。

## 8. 工期、资源与实施节奏

主 Spec 曾确认 **146–227 人日**的首轮全范围粗估，置信度低，包含多角色工程量与风险缓冲；它不是当前剩余工时，也不是单人日历周期。不能用“16/26 已集成”直接扣减该估算，更不能预扣 AI 提效。

本次采用依赖顺序，不给无依据的上线日期。恢复实施后，P0 基于差异清单、已有测试和实际可用投入重新估算剩余工作；P1 样板完成后，用实测交付周期校准后续计划。若需要固定日期，先确认可用人员/投入、目标部署环境与必须交付范围，再形成排期。

默认由陈立承担当前产品、研发、评审、测试、安全等责任；不以缺独立人员作为阻断。实施初期保持串行集成：契约/状态 → 持久化 → 应用服务 → 代表 UI → 回归 → 验收。稳定接口确认后，才考虑 UI 阅读视图、独立测试或文档等非重叠工作并行；本轮没有启动子代理。

## 9. 每段通用交付要求

每段设计、检查点与报告包含：父 POD/里程碑、CAP/Unit、需求和原型版本、实现/集成/验收状态、延期事项与唯一下一路由。产物至少包含确认设计、可审查变更、适用门禁、数据库/API/UI 读回、具名验收和未接受风险。

运行和数据边界：测试使用确定性合成数据、隔离 schema 与明确清理；本地标准库迁移按授权范围执行；新增服务记录 PID/端口/结束条件，结束后关闭或明确交接。涉及部署的阶段提供产物来源、环境、回滚、烟测、观察窗口与监控阈值。

记录最小复盘指标：每段开始/结束、返工次数、失败门禁、缺陷来源和试点问题，用于校准计划，不用于个人绩效评价。

本轮文档完成后，工程仍暂停。下一步是评审 P0 关键口径与 P1 代表页范围；确认后才按收口后的 POD 路由恢复具体实现。
