## 一、平台定位（一句话）

面向**产品经理**从想法到上线**全链路闭环**的作业平台：主体为对话 chat（类豆包），阶段步骤所需的 Skill / MCP / 工具**自主加载与配置**，开发阶段调用 Zed / Codex / VS Code 等本地开发终端并**实时跟踪终端对话流**。

最新产品要求：各阶段高效完成、阶段间无缝衔接。业务需求的可交互候选应能早于完整 PRD 形成，原型与 PRD 草稿共同演进；同一需求持续承接上下文、增量更新成果、集中处理必要决策并可中断恢复。具体目标、八阶段退出依据和 F01–F07 场景见 [29 号“最新产品要求”](29-M2c-3治理与项目方案及范围确认-20260912.md)。R1 已验证其合成交互；治理及R2已验证隔离PG持久化，真实执行和标准业务集成尚未启用，不调整里程碑或正式 POD 路线。

29 号第九节的 R1 已落到原版入口：交互原型与 PRD/验收项共同形成，规则变化按关联基线采纳，八阶段承接、等待决定、未知结果核验和失败恢复均可演练。当前为固定合成模板与模拟执行；这些交互为后续领域方案提供输入，不构成真实 AI 或生产流程。31号确认的M2c-3治理与作业上下文已实现并隔离验证。R2关联版本及阶段承接已验收合并，结果见34。35号方案已在36号实现，让测试准备与原型/PRD同步，串起结果、缺陷、验收和只读发布输入；随后按37号候选方案补发布评审、具名结果、观察与最终复盘。35号59文件/五隔离目标/26闸已获确认并验证通过，不改变正式台账。

## 六、历史任务：M2b-2 前端动作层切领域 API

以下保留交接时的技术锚点，现已按 21/24 号修复并验收；“有 bug”“需跳过”“ID 不冲突”等文字不是当前状态，尤其 ID 假设已由实测纠正。

**目标**：api 模式下作业流（start-run / reject-plan）走领域 API，配合 ws-client 让**终端面板实时滚动对用户完整可见**。

**已探明事实（Codex 默认看不到，必须传入）**：

1. **ws-client.js 有 bug**：查找 run 用 `P.s.runs.find(...)`，实际 run 挂在 **`P.s.reqs[reqId].runs`**（见 model.js P.startRun 第 981 行 `r.runs.push(run)`）；P.tick 遍历 `Object.values(P.s.reqs)` 下 `r.runs`。
2. **P.tick 需跳过领域 run**：给领域 run 打 `_remote = true` 标记，P.tick 循环开头 `if (run._remote) continue;`——避免本地模拟推进（pct+8/生成行）与 WS 推送双写冲突。
3. **分流点**：`run-actions.js` 的 `A['start-run']`（现为 `commit(() => P.startRun(...))`）与 `A['reject-plan']`；api 模式下改走领域 API：
   - start-run → `POST /api/runs`（createRun）→ `POST /api/runs/:id/plan-approve` → `POST /api/runs/:id/start`（有在线 Bridge 则派发，无则服务端回退模拟——诚实标注）
   - reject-plan → createRun → `POST /api/runs/:id/plan-reject`（原因必填，服务端留审计 + warn 通知）
4. **run id 空间不冲突**：前端种子 run id `R-1200+`（P.s.seq 起点），领域新 run `R-101+`（S.seq.run 起点）。
5. **领域 run 合并进前端**：领域 API 返回的 run 字段（id/reqId/status/operation/exitCode）需包装成前端渲染结构（qualityGates/replay/lease/planApproved/budget/lines 骨架——参考 model.js P.startRun 第 914-980 行），push 进 `P.s.reqs[reqId].runs`，设 `P.s.ui.runId`。
6. **WS 推送即驱动力**：sim-bridge 在线时，job.line 由 ws-client 追加到 run.lines 并 render——前端无需再跑 tick 模拟推进。

**验收标准（M2b-2 完成判定）**：

- 前端 api 模式完整链路：对话创建需求 → 确认版本 → 阶段推进 → 发起作业 → 批准计划 → 启动执行 → **终端面板实时滚动 sim-bridge 推送的对话流** → 状态 SUCCEEDED
- local / mock 模式零回归（verify-prototype 6 组全绿）
- 服务端领域 API 状态一致（run 状态/行/回放落库）
- 所有 verify 脚本全绿

## 八、硬约束与用户偏好（全程适用）

1. **无 OSS，文件本地管理**（已多次确认的既定边界；上传材料落本地目录 + sha256）。
2. **诚实标注模拟边界**：模拟执行/合成样例/示意架构必须明示，禁止静默假装真实。
3. **零脑补/禁编造**：数字、结论必须有来源（代码/文档/可复现计算）；无法取得标"待补充"。
4. **务实 MVP / 分阶段 / 排斥过度设计**：先跑通再优化；不做超出当期任务的设计。
5. **技术栈固定**：前端原生 JS（无 React/Vue/构建工具）；后端 Node + Express 4 + ws + jsonwebtoken + pg；PostgreSQL 14+（m1-schema.sql）。
6. **PowerShell 环境**：命令不用 `&&` / `||`（逐段判定）。
7. 文档与代码同步更新（docs\planning\prototype-v3\ 编号续 19）。
