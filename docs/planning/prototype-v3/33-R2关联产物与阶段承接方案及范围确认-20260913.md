## 三、用户如何连续完成工作

### 1. 候选先行，文档随之完善

在想法或需求阶段，用户可先创建、导入或按模板形成候选，不要求先完成 PRD，也不以澄清全部完成作为预览前置。候选允许暂时只有原型，页面同时列出 PRD、验收项和待决定事项的缺口；可以继续编辑和保存，但不能将不完整候选确认成开发输入。

建议来源按实际写入者标识为“手工整理”“文件导入”“平台模板”。模板只支持本文定义的结构化组件，不理解任意自然语言需求；普通聊天仍明确显示当前模拟来源。未来 AI 适配必须由服务端记录提供方、模型/模板版本和输入指纹，浏览器不能自行提交 `source=ai` 冒充真实生成。

### 2. 一处比较，一次采纳

中间对话区展示变更建议卡，右侧画布在“原型 / PRD / 验收项 / 差异”之间切换，左侧显示材料与待决定事项。保留现有三栏和双终端，不新建全屏编辑门户。

例如当前关联组 B1 使用原型 v2、PRD v5、验收项 v3。用户把提醒时间改为3天，建议卡明确列出修改的规则、涉及的产物、引用依据和待重审结论。采纳后形成 B2；只有变化的产物增加版本，没有变化的版本原样引用。不是把三份产物的版本号强制设成相同。

采纳是对一份已展示候选的整体操作；R2 不提供任意字段勾选后跳过一致性检查。用户需要部分采纳时，先修改候选形成另一份可比较建议，再整体采纳。拒绝须保存原因，不修改当前关联组。

### 3. 确认与承接合并为一次业务动作

| 位置 | 用户动作 | 服务端一次事务完成的内容 |
| --- | --- | --- |
| idea | 确认想法并继续 | 延用现有想法确认/推进规则；候选可在此前出现 |
| req | 确认业务方案并进入设计 | 校验完整关联组、材料影响和待决定项；记录业务确认；确认对应 PRD 版本；推进 design；返回设计输入摘要 |
| design | 确认实施设计并进入开发 | 校验当前业务确认、最新设计内容和实施范围；记录设计确认；确认设计版本；推进 dev；返回可创建计划的输入摘要 |
| dev | 创建/批准/启动计划 | 延用现有作业审批；快照绑定关联组和两份确认，继续受当前成员、工具能力及旧计划校验约束 |

业务确认、设计确认、作业批准是三个不同对象。界面减少重复点击，服务端仍逐项验证，不能用“全部通过”按钮隐式授权 Shell、发布或真实工具。

### 4. 变化后告诉用户从哪里继续

| 变化 | 生效处理 | 用户继续位置 |
| --- | --- | --- |
| 原型/PRD/验收项采纳新组 | 旧确认保留为历史，对当前组失效；相关待批计划不可启动；旧运行/证据不删除 | req，重新确认业务差异 |
| 最新设计发生变化 | 业务确认仍有效；旧设计确认不再覆盖最新设计，计划需重建 | design |
| 材料/想法决定变化 | 标记关联输入需复核；列出具体变更引用，未处理前禁止确认/启动 | req；若缺失的是想法决定，先定位该问题 |
| 项目重绑或权限变化 | 延用31号治理规则，并重新计算受影响确认/执行前置 | 明确显示阻断原因及对应位置 |
| 仅保存候选、发消息或重开画布 | 不改变已采纳组和有效确认，不使计划因无关 reqRevision 变化失效 | 保持当前工作位置 |

RUNNING/CANCELLING/UNKNOWN 期间可以准备候选、比较差异；不能采纳新业务基线。先停止并核验同一运行，不自动取消或新建替代运行。WAITING_APPROVAL 期间允许采纳，原计划保留但变为不可批准/启动；用户可按已有方式拒绝/取消后新建计划。

WS 通知只提示事实已变化，页面随后 GET 回读。切换需求时，输入草稿和画布选择按租户、稳定成员、需求、产物/候选 ID 隔离；晚到请求不得把 A 需求画布替换为 B。409/503 保留草稿和原比较对象；相同载荷重试沿用 commandId，成功读回后才清理。

## 四、A方案的领域与兼容契约

### D1 · 一个事实来源，独立版本，固定关联

新增 `004-linked-artifacts.sql`，001/002/003原文件及 checksum 不变：

| 对象 | 内容与不变式 |
| --- | --- |
| req_versions（既有） | PRD 是 stage=req，实施设计是 stage=design；内容只追加新版本，原 confirmed/stale 字段用于兼容读，不作为关联确认的唯一依据 |
| artifact_versions（新增） | 仅 prototype / acceptance 两类；含租户、需求、独立版本号、父版本、内容摘要、来源、作者、时间、内容指纹；不再存第二份可写 PRD |
| artifact_groups（新增） | 固定引用一个 prototype 版本、一个 req_versions PRD 版本、一个 acceptance 版本，以及材料/想法输入指纹；组只追加，reqs 增加当前组指针 |
| artifact_group_sources（新增） | 组依赖的材料版本、想法版本及稳定规则映射；引用目标可独立回读，不用文件路径作为身份 |
| artifact_proposals（新增） | 基线组、输入指纹、建议内容、来源、前序建议、状态、处理人/原因、应用结果；内容不可原地改写，修订时新建建议并显式取代前一份 |
| artifact_confirmations（新增） | BUSINESS 绑定组与输入指纹；DESIGN 另外绑定设计版本和实施范围指纹；记录稳定成员 ID、当时角色、时间、意见。新的确认不覆盖历史记录 |
| artifact_impacts（新增） | 变更原因、旧/新输入、受影响组/确认/计划、恢复位置、处理命令；同一变更不重复生成影响记录 |

新对象均由现有 ID 分配器分配；跨表引用使用租户与需求一致的组合约束，并由服务端校验产物类型。当前组指针只能指向本需求完整关联组；旧组、旧版本和旧确认禁止硬删除或原地替换。指纹由服务端计算，外来 `confirmed`、角色、状态和指纹不能成为可信事实。

004还须更新 id_counters 的实体枚举、message_references 的互斥引用约束，以及003中只允许 snapshot_version=1 的两处约束，使历史v1与新v2都能保存；不能只改JavaScript版本号。迁移注册表保留001→002→003顺序后追加004，PG runtime/readiness显式要求004，缺失或checksum不符即拒绝启动。结构化/原件原型用 `representation=spec|file` 区分；file必须引用本需求材料原件版本，spec必须通过固定结构校验，不能让任意HTML被误当spec执行。

验收项有稳定 `acId`、场景、前置条件、步骤、预期结果和关联 `ruleId`；PRD 的既有 `fields` 内容保留，规则映射单独保存在组内，不要求覆盖历史 JSON。结构化原型节点使用同一 ruleId 引用。服务端校验 ID 唯一、引用存在、必填字段及映射完整；这只能证明结构一致，业务语义一致仍由用户比较确认，不声称算法理解了任意文字。

### D2 · 候选与采纳事务

候选状态为 INCOMPLETE / READY / APPLIED / REJECTED / SUPERSEDED；INCOMPLETE 和 READY 由服务器校验内容决定。保存不完整候选可以预览与恢复；只有 READY 可采纳。替换候选内容产生新 ID，旧候选明确指向新候选，不丢失历史。基线过期由实时比较得出，不依赖后台定时器碰巧执行。

所有写操作沿用 `{commandId, expectedRevision}`、当前成员校验和命令收据。采纳还必须提交 `proposalId + baselineGroupId + inputFingerprint`；无当前组时 baselineGroupId 为 null。加锁顺序统一为治理/成员前置锁 → 需求行 → 候选/关联对象，沿用当前事务机制，避免新增与作业启动相反的锁顺序。

一个事务内重新校验角色、版本、输入引用、活动作业及完整性，追加变化的版本、组和来源，更新当前组，追加影响/审计/领域事件，最后记录收据。任何一步失败则全体回滚。文件原件先完成受控持久化，采纳事务只绑定 READY 对象；失败不能把未入库文件当已采纳版本，沿用并验证现有文件补偿机制。

同 commandId 同载荷返回同一结果；不同载荷拒绝。权限必须在重放收据前复核。业务变化比较组/输入指纹；expectedRevision 处理并发写入，但不把无关消息修订号加入计划内容基线。

### D3 · 权限、确认与旧写入口

沿用当前本地身份模型：owner/executor 可创建候选、采纳、拒绝、业务确认、设计确认；viewer 只读。默认认可陈立同人多角色，但每个确认对象都需要独立记录。不可跨租户、跨需求，停用成员和失去权限者不能继续写入。

**这是 PG 的新增前置规则，需本次明确确认：** req→design、design→dev 及新计划创建都要求关联组与相应有效确认。既有需求没有组时显示“待补齐关联成果”，不得从演示数据补一个组来凑条件。迁移只加结构，不伪造历史确认。

旧版本 GET、旧计划/证据读取保留。旧 PRD 保存和会话差异采纳如果会绕过关联组，返回 `LINKED_WRITE_REQUIRED`（409），带需求和当前组定位；前端转入候选比较流程并保留用户输入。旧版本确认/阶段推进可委托同一确认策略，但不能只改 confirmed 字段后放行。设计保存继续追加既有设计版本，同时使对应设计确认不再有效。想法保存、问题回答、材料更新/影响处理、项目重绑、版本评审“需修改”也必须调用同一影响策略，不能只在新按钮上做校验。后续版本评审“通过”不能自动恢复此前失效的关联确认。

004部署后，旧 snapshotVersion=1 的计划可查看和取消，未启动计划须重新创建并批准 v2；已在运行的历史作业继续沿原 runId 观察/取消/核验，不改写其快照。local/mock/memory 和 R1 保持原模式，不能以其宽松规则替代 PG 前置。

### D4 · 来源与隔离预览

R2 推荐先落实两条明确路径：

1. **结构化交互原型**：用户编辑或导入 `prototypeSpec` JSON，支持 page/section/text/field/select/button/table/dialog，以及切页、展开、校验必填、切换状态等枚举动作。每个节点有稳定 ID 和可选 ruleId；最多10页、每页100节点、500条合成表格行，总内容≤256KiB。字段只收数据，不收任意 JS、HTML、CSS、URL、代码表达式；不引入拖拽设计器或开放插件执行器。
2. **现成文件原件**：在既有受控上传路径中增加 .html 原件保存、版本关联、转义源码查看和明确触发的下载；复用 PNG/JPEG/GIF 查看。原件字节和 hash 不变。任意 HTML 内的脚本、外链和多文件工程在平台内**不执行**，界面明确“原件已保存，交互运行尚未接入”。仅导入 HTML 不能标为已完成交互验证；业务确认必须另有结构化可体验候选或明确的人工原件评审记录，记录接受的预览限制。

受控原型由平台固定渲染器解释 JSON，在独立 sandbox iframe 中运行。仅允许固定交互脚本，不允许 same-origin、弹窗、表单网络提交、顶层跳转、自动下载、凭据或 Bridge 通道；用户文字以文本节点写入，不拼接成脚本。模板内资源只使用平台固定内容，不接受用户提供的资源地址。预览数据不回写业务事实，保存和采纳必须回到父工作台明确操作。

iframe 的 sandbox 不能被当作任意 HTML/JS 的完整安全方案；尤其不得同时放开脚本和同源权限。相关浏览器约束已查阅 [MDN iframe 文档](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)。实施必须补浏览器攻击样例、网络请求观察、父页面隔离和资源释放证据，不能凭文档声明安全。

这是本轮能力边界，**不承诺导入任意 HTML 后交互无损运行**。如果本轮必须支持这一点，需改选扩大的独立预览运行方案，先补运行隔离、网络策略、资源包、进程/超时和验证包，再实施，不能现场解禁上传脚本。

### D5 · 可信引用与下一阶段输入
