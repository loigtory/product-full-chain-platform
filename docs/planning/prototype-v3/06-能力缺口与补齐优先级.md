## 3. 聊天附件的选定方向建议

建议保留输入框位置，将“＋”改为附件菜单：上传文件、引用已有材料、引用当前产物。拖拽文件与粘贴截图进入同一个发送前队列。材料区继续承担长期资料管理，不要求用户每发送一次临时参考都先完成一张登记表。

附件归属分为两种用途：

- **本轮参考**：随消息提交，只有本轮显式使用；原型可预选此用途。上传动作不自动修改已确认需求基线，也不自动回退阶段。
- **纳入需求材料**：复用同一文件资产，创建材料版本/使用关系；存在既有确认时进入材料影响评估。不要重新上传第二份文件。

原型可以模拟PDF/Word/表格解析，但需明确区分“接收成功、解析中、可引用、解析失败”；接收成功不表示已分析。图片至少展示本地缩略图及放大预览，表格显示工作表/范围选择的交互。无法读取、超限、格式不支持应定位到具体附件，允许移除或重试，不能只弹一个整体失败提示。

推荐消息概念结构为 `messageId / turnId / requirementId / stage / text / attachmentRefs / contextSnapshot / status`；每个引用绑定 `assetId + assetVersionId/hash`，必要时带页码、工作表、行列或段落定位。UI草稿与已发送消息分开；重试沿用请求幂等标识，重新提问形成新回合。具体字段仍需对照正式 contracts 和来源权限设计确认。

状态示意：选中 → 准备/校验 → 待发送 → 接收/解析 → 可用于本轮；任一步失败都保留文件卡与原因。刷新后的原件可用性、发送时切换需求、移除尚在读取的文件、文件重名/版本不同、一次多个失败项，均需在原型表达并纳入用例。二进制留存应使用适合文件的存储机制，不能将大文件直接塞入 localStorage。

平台路径输入与上传是不同来源：网页上的本地路径文字不代表浏览器取得文件读取权限；选择已配对电脑的路径应走 Bridge。下一版文件引用需能区分“浏览器附件”“需求材料”“工作区文件”和“已登记连接器来源”。

## 4. 此次发现的具体规则问题

这些是从当前代码直接发现的简化点或缺陷，后续迭代需先补回归，不能按现状固化接口：

1. `q.impact` 是单个材料ID，连续登记多个待评估材料会覆盖前一个指针；应改为独立待处理影响集合。
2. 对话建议只保存 action/label，没有稳定的目标版本或作业ID；旧消息按钮点击时可能作用到新的当前对象。生成建议时应绑定对象与基线，过期后提示重新评估。
3. 搜索某个 runId 只跳到开发终端，没有传入找到的 runId；同一需求有多次运行时可能显示另一条运行。应传递准确运行定位并验证。
4. `save-scope` 重新按行号创建Unit/AC，追踪视图按索引组合；编辑或重排后不应更换对象身份或自动建立无依据关联。
5. `testRun` 覆盖 `r.tests`；失败测试详情无法按旧批次展开，只有摘要事件。修复验收需要保留每个测试批次和准确基线。
6. 新需求使用固定提醒类示例AC；对其他业务只能作为待替换示例，不能默认当成已完成需求拆解。需要从当前输入提出候选并明确确认。

## 5. 补齐后如何判断足够指导开发

通过三条端到端任务验收，而不是只检查按钮能否点击：

| 任务               | 用户走查                                                                                        | 退出证据                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 用资料形成需求     | 拖入Word与规则表、粘贴截图 → 给出分析诉求 → 查看解析与引用 → 回答问题 → 采纳草案 → 下载明确版本 | 消息与附件对应；答复可追溯来源；未采纳不改变基线；导出内容与画布版本一致                |
| 在已有需求上修改   | 引用当前方案某段 → 提出变更 → 查看差异 → 部分采纳 → 重新评审 → 更新下游待办                     | 已确认正文不覆盖；建议不串需求/版本；改变范围时具体影响可读                             |
| 由开发结果完成交付 | 选择工作区 → 按范围执行 → 查看文件差异/日志 → 打开预览 → 反馈缺陷 → 重试/复测 → 获取交付包      | 运行与消息关联；失败有恢复；停止答复不等于取消进程；代码/测试/验收/发布绑定同一交付快照 |

另以空文本纯附件、重复点击发送、断连、解析失败、上传中切需求、刷新恢复、只读、过期引用和取消重试验证异常。原型中可用合成解析/AI输出，文件选择、预览、消息引用、采纳新版本和下载应提供可操作体验。

### 7.2 规则问题修复

1. `q.impact` → `q.impactList` 队列（`model.js` 工厂/迁移 + `actions.js` save-material/apply-impact/exclude-impact），连续登记不互相覆盖。

4. `save-scope` 按名称保留已有 Unit/AC 的 id 与状态，仅真正新增项分配新 id（`actions.js`），不再按行号重建身份。

6. 新需求 AC 由目标/名称关键词生成候选并标注“由输入候选，待业务确认”（`model.js` makeRequirement），不再默认沿用提醒类示例。

### 7.4 残余限制（如实声明）

- 发送时仍在打字的上一条模拟答复会被 flush 为全文（演示级取舍，已实现但非正式语义）；
- 工作区运行与文件变更、失败定位日志为合成演示数据（`model.js` 演示文件），正式由 Bridge 读回真实文件与 Git 差异；
- 附件二进制不持久化到 localStorage（仅元信息/缩略图/小文本），刷新后原件需重新上传，界面已标注“只保存在当前浏览器会话”；
- PDF/Word/XLSX 正文为“演示解析”占位，正式接入对象存储与解析服务。

正式开发路线、P0–P4 与验收状态不变；本回填仅提升原型可操作闭环，用于指导正式 contracts 设计。
