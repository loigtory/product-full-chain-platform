## 1. 目标与非目标

T2 建立后续 T3-T7 共用的服务端权限和跨 CAP 依赖边界：

- 定义已认证 `ActorContext`、需求级动作、权限快照、敏感材料访问和本次动作授权契约。
- 在 application service 前提供统一对象级授权服务；授权能力不可用、身份/成员/敏感等级/动作授权未知时一律拒绝。
- 定义 `AuthorizationPort`、`ArtifactEvidencePort`、`GateExecutionPort`、`DeliverySummaryPort` 四个版本化端口。
- 提供默认 unavailable adapter，以及仅允许在 `local/test` 显式启用的确定性 fixture adapter。
- 返回 `capabilityVersion`、`status`、`checkedAt`、安全原因码和 fixture/unavailable 来源，不以空对象、默认值或 PASS 掩盖依赖缺失。

本轮不新增业务 API、页面或数据库 migration，不实现真实 PFC-02～05 调用，不读取或传递材料正文，不进入 T3，不运行默认 `pfc` migration，不提交、推送、部署或连接外部环境。

## 2. 已确认方案

采用 G9-A 已确认的服务端策略边界：

1. `packages/contracts` 维护 Actor、权限、依赖状态和四端口的版本化类型。
2. `packages/domain` 维护不依赖网络/数据库的 fail-closed 权限判定规则。
3. `apps/server/access` 调用 `AuthorizationPort` 并在业务 service 前形成允许或拒绝决定；拒绝结果只带脱敏审计摘要。
4. `apps/server/dependencies` 装配 unavailable/fixture adapters；未配置真实依赖时默认 unavailable。
5. fixture adapter 不内置成功事实，只读取调用方提供的确定性 fixture；找不到精确数据时返回 UNKNOWN。

没有选用浏览器侧权限判断，因为按钮显隐不能保护业务对象；没有把 PFC-02～05 stub 成默认成功，因为这会破坏 fail-closed 和可审计边界。

## 3. 权限矩阵

| 场景                | 必要条件                                                           | 结果                                         |
| ------------------- | ------------------------------------------------------------------ | -------------------------------------------- |
| 查看需求            | 已认证；团队成员或需求成员；动作在授权快照中                       | ALLOW                                        |
| 无需求范围          | 团队和需求成员均为否                                               | `PERMISSION_DENIED`，不返回正文              |
| 授权能力不可用/未知 | AuthorizationPort 为 UNAVAILABLE/UNKNOWN，或快照关键字段未知       | `PERMISSION_DENIED`                          |
| 内部普通材料        | 有需求范围及查看动作                                               | ALLOW；传递只允许已批准 AI/Skill 目标        |
| 内部受限材料        | 有需求范围、查看动作及显式受限成员权限                             | ALLOW 查看，否则拒绝                         |
| 受限材料传递        | 上述条件加精确覆盖 actor、需求、目标、用途和材料范围的当前动作授权 | ALLOW，否则 `SENSITIVE_ACTION_AUTH_REQUIRED` |
| 可公开材料          | 仍需需求范围和动作权限                                             | ALLOW；不产生匿名发布或外部传播授权          |
| Question 确认       | 授权快照明确允许目标动作                                           | ALLOW；非 Owner/职责角色由 PFC-04 快照拒绝   |
| 权限撤销            | 最新快照不再允许或端口状态未知                                     | 立即 DENY；不复用旧结果                      |

## 4. 端口降级与配置

| 端口                 | 默认行为                         | fixture 行为                                 | 真实能力进入点 |
| -------------------- | -------------------------------- | -------------------------------------------- | -------------- |
| AuthorizationPort    | UNAVAILABLE，所有业务访问拒绝    | 精确 actor+requirement fixture；缺项 UNKNOWN | PFC-04         |
| ArtifactEvidencePort | UNAVAILABLE，不返回材料或证据    | 只返回 EvidenceRef 元数据 fixture            | PFC-02         |
| GateExecutionPort    | UNAVAILABLE，不创建自动运行      | 只返回显式配置的合成回执                     | PFC-03         |
| DeliverySummaryPort  | UNAVAILABLE，缺证保持 BLOCK/WARN | 只返回显式配置的合成摘要                     | PFC-05         |

`FIXTURE_ADAPTERS_ENABLED=true` 仅在 `APP_ENV=local/test` 有效；任何其他环境启动装配时立即失败。fixture 结果必须标记 `source=FIXTURE`，unavailable 结果标记 `source=UNAVAILABLE`。

## 6. 验证、验收与回滚

- TDD：先确认 contracts、权限矩阵、端口降级和配置隔离测试因缺少实现而失败，再实现最小代码转绿。
- 开发门禁：目标测试和 quick；交付门禁：Core。Full 保持 fail-closed，直到 T3+ 的 API/UI 权限、并发、恢复、安全和性能覆盖齐备。
- T2 技术退出：AC 01-05、02-11、03-05、04-08/10、05-05/06 及 CAP AC 08/11/12 的 T2 基础规则均有自动化证据；默认 unavailable 和非本地 fixture 禁止均通过。
- T2 不形成独立业务验收。代码评审、测试和安全责任人现统一登记为陈立；本计划仍最多登记“技术实现候选通过”。
- 回滚只涉及本轮未提交 T2 源文件和测试；不回退 T1，不执行 Git destructive 命令，不改数据库。
- 停止条件：发现权限默认放行、受限材料范围泄露、fixture 可在非本地启用、端口不可用被映射为成功，或需要改变已确认角色/权限规则。
