## 3. 连续交互

1. **提前准备。** 已有交付基线后，在开发/测试/验收阶段可“准备发布草稿”；自动带入需求、项目、交付对象、变更/回退摘要和已存在的测试/验收版本。缺失项清楚显示，允许保存不完整草稿。
2. **复用并核对差异。** 产品验收通过后，主动作变为“核对发布准备”。自动比较草稿依据与当前版本；用户确认更新依据，保留自己填写的环境、依赖、监控等文字，不自动沿用旧批准。
3. **集中评审。** 左侧显示来源版本，主区展示范围/目标/回退/监控与缺项，右侧查看原件和历史。当前Owner一次确认准备检查和意见，具名记录；不重复签已经有效的测试/产品验收。
4. **登记实际结果。** 明确按钮为“登记发布结果”，不写“执行部署”。成员只填实际起止时间、结果、实际版本、授权依据及证据。未知结果显示“核实原记录”，不建议再次发布。
5. **直接承接观察。** 成功结果和冒烟均为具名通过、版本一致时，冻结观察计划、进入observe。沿用目标/指标/来源/责任人；每次追加实际值和证据，保留完整记录。
6. **完成最终验收。** 自动列出目标与实际差异、异常和遗留事项。Owner确认最终业务结论，通过才关闭；驳回留下原因，修复经显式回流形成新交付和新发布轮次。可预填一条现有知识表单，用户确认后另行保存。

保持当前聊天、附件、画布、证据和阶段导航。release/observe的聊天支持附件及派生报告版本，新增消息不会改变发布基线。空/加载/无权限/证据不可用分别可见；写失败保留草稿、错误定位可聚焦；写后读回失败保留commandId并核验同一提交。409比较并重新确认依据，403身份变更隔离旧草稿，503保留输入；跨需求、成员和服务地址的晚响应不得污染当前页面。42个脚本按依赖加载，新五模块复用原版组件、样式和焦点规则。

## 4. 待确认规则 D1–D8

### D1 · 结果与授权来源

仅允许 `USER_REPORTED`，冻结登记成员ID/姓名、服务端登记时间和用户填报的实际时间、环境标识、版本/构建引用、附件版本及摘要。客户端传CI_VERIFIED/AI_EXECUTED等来源应拒绝，Git/构建号只作声明，不探测URL、不执行上传内容或任意路径。

**准备评审通过是平台内记录，不赋予真实环境执行权限。** 准备单中结构化记录外部授权的声明：授权编号、环境/目标、版本或范围摘要、动作类型、适用起止时间、授权人/责任人、证据。发布结果的实际时间及目标须落在此声明范围内；UI仍标明“授权依据由成员提供，未外部核验”。凭据不得填入字段或上传证据。角色均为现有本地Owner/Executor/Viewer，不新增组织授权/SSO模型。

开发/测试中只生成CODEx_TEST_数据；合成的成功、指标和签字字段不能充当真实上线证据。API、下载报告和界面必须保留同一来源标识及 `executionAvailable:false`。

### D2 · 准备版本、评审与失效

发布计划采用整体追加版本，状态DRAFT / READY仅描述完整度；保存新草稿不取消现行批准。评审状态单列NOT_SUBMITTED / PENDING / APPROVED / REJECTED / SUPERSEDED。绑定需求、项目、交付/测试批次/验收报告ID与内容指纹，提交评审时只允许当前release阶段、inputsReady、无活动/取消中/未知作业及未关缺陷；提交冻结当前计划内容和依据，生成站内待评审通知，不发邮件/IM。

准备内容包括：准确发布范围、唯一环境/目标、实际交付对象、依赖及影响、发布负责人、预期动作、回退对象/步骤/触发器、冒烟清单、观察窗口、目标指标/口径/来源、监控与告警负责人、授权声明及证据。没有依赖/风险可明确填“无”；空模板和“待补充”不满足READY。

Owner对确切计划版本记录APPROVED或REJECTED及意见；同人兼任提交/评审角色允许但实名留痕。每条需求仅一个当前批准。新的批准取代旧批准；被驳回或替代记录不可改写，修订须新版本。批准使用业务指纹，不能因聊天revision变化而作废。

批准前以及首次成功登记前，绑定业务/设计/开发/套件/测试/验收/项目/证据变化使当前批准不再放行，显示差异并沿R2/R3回流。发布范围、环境、负责人、回退、授权或监控计划变化也须新版本再评审。历史批准仍可查看。当前批准人停用/降权后不能支撑新发布记录，由当前Owner重新评审。

### D3 · 发布结果、未知核验与回退记录

每次发布尝试冻结计划/批准ID；成员录入实际起止时间、实际环境/版本、结果SUCCESS/FAILED/UNKNOWN、冒烟项PASS/FAIL/NOT_RUN及说明。SUCCESS/FAILED均须附件证据和实际结束时间；UNKNOWN允许结束时间为空，至少有实际开始时间、定位线索、责任人、最近核查时间和说明，不得标记成功。时间必须为有效UTC值，开始≤已知结束≤服务端当前时间，已知执行区间须在所声明授权有效窗口内；UNKNOWN至少验证开始时间并保持阻断，核实终态时补校验完整区间。迟到登记不按登记时刻误判过期。

只有当前有效批准、版本/目标相同、SUCCESS、全部计划冒烟PASS、证据有效，才原子生成发布报告并进入observe。服务器只证明该记录符合规则，仍不证明部署发生。FAILED留在release，展示处置；新的尝试需新计划版本和Owner评审。每轮最多一个未解决UNKNOWN；未知后只追加带previousRecordId的核实记录，不自动再发起尝试。核实结果必须仍绑定原计划/目标，来源不变。

回退同样是单独的人工记录，关联原尝试、批准中声明的回退目标、实际时间/结果/证据。回退失败或未知阻断最终通过；回退成功结束当前观察并标记该发布轮次已回退，不能把旧发布改成“未发生”。未解决的发布或回退UNKNOWN不能开始新轮次，也不能用客户端声称的重试覆盖。旧 `/execute`、`/rollback`、`/cicd` 端点保持不可执行，返回明确CAPABILITY_UNAVAILABLE；人工回退使用新`/reported-rollbacks`，不混用执行语义。

### D4 · 观察计划和指标

观察窗口按计划固定1–168小时，默认24小时；从具名发布成功的实际结束时间计算。UI显示服务端计算的截止时间和剩余时间，客户机时钟/演示快进不影响门禁。允许迟到登记已完成的实际观察，但要求实际观测时间落在该发布之后，最终覆盖窗口结束时点或更晚，不允许未来时间或拿旧发布数据充数。

计划内1–20个稳定metricId，包含目标、单位/统计口径、来源、采样说明及负责人；需要对照时填基线值。每次追加指标记录包含metricId、实际值、采样区间、来源说明、达标/未达标/未知、影响说明和证据。达标结论为具名判断，不由模拟数据、后台计时或AI自动替代。指标未记录/未知/未达标、冒烟失败、证据不可读及当前异常未解决时，最终通过阻断。

观察不能仅靠“等待24小时”通过：至少每项指标都有窗口末端有效记录，并由Owner核对口径、来源和目标对比。追加异常登记、处置、复核使用连续事件，不删历史失败记录；同一指标必须带预期前记录和序号，冲突返回409。目标/口径冻结，不能通过降低目标把结果改成通过。

### D5 · 最终验收、遗留项与发布后变更

Owner最终结论ACCEPTED / REJECTED，独立于产品验收和准备评审。提交前展示被冻结的业务目标/AC、发布/观察报告、指标差异、阻断项和遗留项。ACCEPTED要求窗口结束、发布成功未回退、证据有效、全部目标达标、无未解决阻断项；填写实际业务结果、结论和复盘，并显式确认非阻断遗留风险。

遗留项包含稳定ID、内容、关联指标/事件、是否阻断、当前有权负责人、截止时间、状态OPEN/IN_PROGRESS/DONE、完成说明及证据；最多50项。阻断项未完成不得通过；非阻断项允许带明确Owner/时限和风险确认关闭需求。最终结论冻结遗留快照；之后只可追加非阻断遗留项处理记录，不改当时验收。结案不自动创建外部任务或发送通知到外部系统。

REJECTED保留observe和未关闭状态；补证后可再次验收。确需改产品或开发时，Owner“返回修复”记录原因和returnStage（req/design/dev），停止当前观察、使旧放行失效、按既有规则增加相关epoch/置旧版本stale；再次经过业务/设计/新开发交付/测试/产品验收和新发布轮次。新发布必须使用新的开发版本，不允许复用失败部署形成的旧PASS直接重发。

**已登记成功后，业务/开发/套件/测试事实不允许被普通写入口直接改成另一条现场基线。** requirement、artifact、verification三个事务入口统一调用release-guard；只读、聊天、新的非业务附件、证据访问撤销、发布/观察记录不被一刀切禁止。材料替换/引用采纳、版本保存/确认/评审/差异采纳、套件采用、补测试/缺陷均须显式返回修复。证据撤权始终允许，并会阻断后续采用/验收；历史快照不被删除。

关闭写 `closed_at`，导航仍停留observe以便读历史，不增第九个阶段。结案后不原位改业务或重开旧发布，后续需求通过既有创建入口带入原需求/报告引用文字，另起明确范围；不复制旧通过结论。可“沉淀复盘”为现有知识创建表单的预填草稿，内容带来源需求、发布/复盘报告ID，用户确认后使用现有API与独立commandId。知识保存失败不撤销已经成功的验收，显示待重试且不重复创建。

### D6 · 权限、证据与事务

Owner/Executor可准备计划、登记发布/回退/观察与遗留处理；仅Owner可批准/驳回准备、最终验收和返回修复；Viewer只读，停用成员拒绝。所有新写入在幂等回执之前重新校验当前成员及Owner限制；跨租户/需求目标404隐藏。当前动作使用当前权限，不能凭旧JWT/旧成功回执绕过降权。

沿用成员/租户 → 需求 → 计划/尝试/观察的锁顺序、expectedRevision和commandId；载荷摘要含完整URL目标。相同命令重放返回同一原结果并要求客户端刷新当前有效性；换目标/内容冲突。领域事实、当前指针/epoch、版本投影、审计、事件和回执同一事务。刷新失败不改变已提交状态，重试不重复批准、创建观察或结案。

release_refs只允许本需求受控附件版本，复用material_versions/file_objects，不接受任意本地路径或远程抓取。准备放行使用当前有效证据；历史详情按冻结版本读原件和摘要，替换当前附件不改历史版本。当前访问被撤销、原件丢失/摘要错误时保留安全元数据及“证据不可用”，不泄漏内容或伪造完整；后续验收仍阻断。观察附件可追加，不自动成为业务输入。

006用复合外键/唯一约束验证租户、需求、计划、批准、尝试、观察和引用属主，结果/评审/事件/最终结论不可UPDATE/DELETE。派生release/observe报告只能由专属服务追加，SQL和通用save/confirm/review/diff共同阻止改写。关闭后的历史不因成员离职变成“从未验收”；新的采纳/确认仍校验当前权限和证据有效性。

### D7 · 规模、性能和故障边界

每需求最多100计划版本、每计划最多20次评审、发布结果/核实/回退事件合计200条、每观察最多2000指标/异常/遗留事件；20指标、50遗留项、每字段4000字符。请求/摘要≤512KiB；每条最多20证据、合计50MiB，单文件及原件总量沿用10MiB/100MiB。分页默认20/最大100、offset≤10000，列表不展开所有历史原件或正文。超过上限明确413，禁止静默截断或旧记录覆盖。

沿用DB池2、SQL超时3秒/空闲事务5秒、新接口请求12秒，超时保持原commandId供核验；没有后台自动执行/采样/重试作业。模型/外部API用量为零，实际多人规模与部署费用未测。数据增长在本轮有界，长期归档/容量策略在业务启用前确认，不以自动删审计实现限额。
