## 1. 分类与授权边界

T3 是 strict 级系统迭代，改变用户可见 PC 工作流、HTTP API、数据库事务、对象权限和恢复语义。实施范围继承已确认 G9-A 的 `T3`：

- 需求清单、搜索、范围筛选、表格/按阶段视图和详情读取。
- 名称与原始想法两项必填的最小 G0 草稿，以及信息齐备的完整 G0 草稿。
- 缺项草稿补齐、首个 MaterialBaseline 形成、G0 `BLOCK -> NOT_STARTED`，不产生 G0 PASS。
- 同名不同 ID、明确失败无部分对象、幂等重放、结果 UNKNOWN 后只读核验和恢复。
- T2 对象级权限在 API 前强制执行；无权详情不读取或返回正文。

本轮不实现 T4-T7，不运行 GateRun、材料影响、SSE、发布或外部 CAP 真实调用；不新增第三方依赖；不运行默认 `pfc` migration；不提交、推送、部署或写入外部环境。

代码评审、测试和安全责任人现均登记为陈立，人员数量或独立性不阻止本地开发和自动化验证。正式代码评审、测试、安全与 T3 接受结论仍分别以实际证据记录，且不扩大提交、发布或外部写入授权。

## 2. 方案与取舍

采用方案 A：`contracts -> application service -> repository port -> Postgres/in-memory adapter -> Fastify -> React` 的模块化单体纵切。

| 方案                                               | 优点                                                                 | 风险/成本                            | 结论   |
| -------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------ | ------ |
| A. 应用服务统一授权、幂等、恢复，API/UI 只消费 DTO | 权限与恢复语义集中；Postgres 和测试 adapter 可独立验证；符合既有边界 | 需要补充 repository port 和 DTO      | 采用   |
| B. Fastify route 直接操作 Kysely                   | 文件少                                                               | 授权、事务、错误和恢复散落；难以测试 | 不采用 |
| C. React 使用静态样例、后续再接 API                | 页面快                                                               | 会把原型模拟误当实现，不满足权威恢复 | 不采用 |

列表 repository 只返回不含 `originalIdea` 的投影；应用服务逐对象调用当前 AuthorizationPort，过滤无权项。详情先读取不含正文的访问元数据和敏感等级，授权通过后才读取正文。尚未登记敏感等级的 G0 草稿按 `RESTRICTED` 保守处理。

## 3. API 与错误契约

| 方法/路径                                         | 结果                                | 控制                                              |
| ------------------------------------------------- | ----------------------------------- | ------------------------------------------------- |
| `GET /api/v1/requirements`                        | 授权范围内的分页清单、部分依赖 WARN | `scope/search/cursor/limit`；不返回原始想法       |
| `POST /api/v1/requirements`                       | 创建最小或完整 G0 草稿              | `Idempotency-Key` 必填；明确失败原子回滚          |
| `GET /api/v1/requirements/{id}`                   | 当前详情、G0 缺项、基线和 gate 投影 | 先授权后读取正文；无权返回 403                    |
| `PATCH /api/v1/requirements/{id}/g0-registration` | 补齐缺项并形成首个 baseline         | `Idempotency-Key` + `If-Match`；名称/想法不可覆盖 |
| `GET /api/v1/requirement-submissions/{key}`       | 核验创建请求结果                    | 只读；返回 CREATED/NOT_FOUND/UNKNOWN，不触发重试  |

错误固定包含 `code/message/requestId/retryable/recoveryAction`；版本冲突附 `currentVersion`，幂等冲突不回显正文或请求 hash。输入超过边界时明确拒绝，不静默截断。

## 4. 事务与恢复

1. 创建事务写 Requirement、可选首个 MaterialBaseline、幂等记录、timeline 和 outbox；同 actor+route+key+同请求 hash 读回同一结果，不同 hash 返回 `IDEMPOTENCY_CONFLICT`。
2. 补齐事务锁定 Requirement，复核 `row_version/current_stage/current_baseline_id`，写 baseline、更新当前指针和版本、幂等记录、timeline/outbox；任何失败全回滚。
3. UNKNOWN 是客户端对传输结果的判断，不把未知解释为成功或失败。UI 保留原幂等键并禁用直接重提，只调用只读核验；确认不存在后才生成新提交机会。
4. 清单搜索、范围和视图切换不写业务状态。视图参数保存在 URL，刷新后重新读取服务端权威状态。

## 5. 测试数据设计

| 项目       | 设计                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| 场景       | 至少两条有权需求；完整/缺项/同名；无权；跨 CAP 摘要 UNKNOWN；创建成功/明确失败/结果未知；补齐成功/版本冲突/其他来源缺说明 |
| 数据源     | `packages/test-data` 确定性 T3 factory；只用合成本地数据                                                                  |
| 标识       | `CODEx_TEST_` + runId；actor/team/requirement/baseline/idempotency/timeline/outbox 可定位                                 |
| 业务有效性 | 六类来源、五类用途、三级敏感边界；缺项草稿没有 baseline；完整草稿只有一个当前 baseline                                    |
| 权限组合   | 产品经理有权、团队/需求成员、无权用户、授权 UNKNOWN、受限成员有/无                                                        |
| 边界/负向  | 空白、过长、OTHER 无说明、同名、重复 key 同/异请求、过期 If-Match、无权限正文、依赖 UNKNOWN                               |
| 隔离       | unit/API/UI 使用进程内 adapter；Postgres 使用 `codex_test_` 独立 schema；不写默认 `pfc`                                   |
| createdIds | 报告记录 runId 和合成 ID；数据库测试结束删除隔离 schema                                                                   |
| 敏感数据   | 不使用真实用户、需求正文、客户信息、cookie、token、密码或连接串                                                           |

设置超过三步且覆盖 CRUD、状态、权限、版本、边界和负向路径，确定性 factory 为强制项。

## 7. 版本、并行、风险与回滚

- 当前版本仍为 `CAP-PFC-01 V0.1 / PFC01-W1`；T3 完成只形成 W1 技术候选，不进入 G10/G11/G12。
- 不使用并行代理；API、repository 和 UI 契约耦合，由当前控制器串行集成。
- 主要风险：授权前读取正文、重复创建、补齐部分提交、旧版本覆盖、UNKNOWN 直接重试、fixture 进入非本地环境。对应以负向测试和 fail-closed 配置阻断。
- 回滚仅删除或反向编辑本轮未提交 T3 文件；不使用 destructive Git 命令，不回退 T0-T2，不删除默认 schema 或非测试数据。
- 停止条件：发现无权正文泄露、重复业务对象、非隔离数据库写入、真实 PFC-02～05 调用、fixture 可进入 preview/staging/production，或实现需要改变已确认产品规则。
