# 11-平台定位、市场对标与能力吸收总结

日期：2026-09-12
范围：PFC 产品全链路平台（原型 `output/pfc-workbench-prototype`）
目的：沉淀"平台定位验证 → 市场对标 → 薄弱点吸收 → 存储边界"的完整决策链，作为后续工程实现的输入

## 一、平台定位（已确认）

- **作业主体**：产品经理——从想法到上线全链路的闭环作业平台，chat 为唯一主作业形态（类似与豆包对话）
- **链路**：想法 → 需求 → 设计 → 开发 → 测试 → 验收 → 发布 → 观察复盘（8 阶段门控）
- **能力形态**：Skill / MCP / 工具自主装载配置（配置中心）；开发阶段调用 Codex / Zed / VS Code 等终端并实时跟踪对话流
- **治理嵌入**：角色权限、审计留痕、预算、材料权限门（受限材料不喂 AI）、阶段绑定、多设备租约
- **AI 触点**：全链路贯穿但分三档——生成（想法/需求/开发）、建议（设计/测试/验收辅助）、只读工具调用（MCP 读文档/查库）；发布阶段刻意无 AI 生成，走审批与规则

## 二、市场验证结论（2026-09 公开资料核验）

**结论：当前无人完整做出"PM 为主体 + 全链路 + 企业级治理"的组合；该位置是真空区。**

| 现有玩家 | 覆盖 | 缺什么 |
|---|---|---|
| Devin（Cognition） | 代码端：自主 agent、多 agent 舰队、Desktop 统一管理、Knowledge/Playbook | 只覆盖开发交付；无 PM 需求/验收/复盘闭环、无业务侧治理 |
| Copilot Workspace（GitHub） | issue→plan→PR，brainstorm agent 向需求上游试探 | 仍在代码上下文内，无 PM 全流程 |
| Jules（Google） | 云端 VM 任务池（60 并发）、plan-approve-PR 硬门 | 纯开发任务执行，无业务链路 |
| Lovable / Bolt / v0 / 百度秒哒 | prompt→可部署应用，非开发者友好 | 生成应用，无阶段门控/验收/治理/审计 |
| Linear AI / Notion / Rovo / Productboard | 需求管理 + AI 辅助（triage/摘要/反馈综合） | 不交付代码，不闭环到上线 |
| PM 个人工具链（市面教程） | 用 Cursor + 扣子 PRD Skill + Stitch + AI Studio 手工拼装 | 个人工作流而非产品，无治理无协作 |
| **PFC（本方案）** | 全链路 + 治理 + PM 主体 + 多终端编排 | — |

**前沿性判断**：组合前沿、单项成熟——AI 编程/agent 编排/chat/MCP/阶段门均为 2026 年标配；差异化与护城河在"流程编排 + 企业治理 + 内网落地"，不在模型能力。窗口约 12-18 个月，巨头上下夹击（GitHub/OpenAI 往下、Lovable/秒哒往上、Linear/Notion 加 agent 闭环）。

## 三、薄弱面与吸收动作

### 3.1 七大薄弱面（现状 → 参照 → 吸收）

| 薄弱面 | 原型现状 | 市场参照 | 吸收动作 |
|---|---|---|---|
| A. 执行端深度 | Bridge 仅登记不连接；终端为合成输出；无沙箱/回放/并行 | Devin 云沙箱+本地双模、会话全文搜索；Jules 任务池+审批硬门 | 沙箱执行+快照回放；开放协议（MCP/ACP）可插拔 agent；计划审批硬门；并行任务池与限流 |
| B. 上下文与知识 | 需求级 messages/materials/refs；无跨需求沉淀 | Devin Knowledge/Playbook；Copilot plan+brainstorm；Linear 自动提炼 | 组织级知识库（复盘/规范/契约沉淀，新需求自动检索）；Playbook；跨需求上下文继承 |
| C. 质量门客观化 | AC 核对/测试/版本/evidence 均靠人看 | Devin verification loop；Copilot 测试门+CI | lint/单测/覆盖率/构建/安全扫描自动进阶段门；AC↔自动化断言↔线上指标绑定；发布后异常自动回滚 |
| D. 治理合规（相对强） | 角色/权限/审计/预算/材料门/租约 | GitHub Copilot IP indemnity | SSO/身份/租户隔离；合规审计导出；多级审批流（PM→技术→合规） |
| E. 协作与生态 | 单机演示 + 飞书文档 skill | Lovable GitHub 同步+一键部署；秒哒接企微 | Jira/飞书/企微/GitLab/CI/监控/数仓双向集成；评论/@/通知流；部署回滚与 CI 打通 |
| F. 数据与洞察 | 观察复盘靠手填/合成 | Productboard/Dovetail 自动汇聚；指标自动拉取 | 客诉/埋点/反馈自动接入；需求↔指标绑定（上线自动取数复盘）；情报源接入 |
| G. 平台底座 | localStorage 单机演示 | 所有商用平台 | 服务端会话/多租户/LLM 网关（模型路由·成本·限流）/审计存储；文件存储见第五节 |

### 3.2 吸收优先级

- **P0 · 立即做（不依赖外部系统，进 MVP）**：① 计划审批硬门（plan-approve）② 客观质量门自动执行（lint/测试）③ 复盘结论→知识库反哺 ④ MCP/ACP 开放协议 ⑤ SSO/租户隔离
- **P1 · 规划做**：沙箱执行+快照回放 · 并行任务池 · 指标自动接入（埋点/数仓）· CI/CD 部署回滚打通 · Playbook 引擎 · Jira/飞书/企微双向集成
- **P2 · 顺手做**：通知流 / 评论@ / 审计导出报表
- **放弃 / 再评估**：自研模型 · 移动端 · IP 赔偿承诺（后者靠生态与法务）

**核心判断**：骨架不缺，缺"执行可信度（沙箱/审批/质量门）"与"知识复利（沉淀/反哺/集成）"——前者解决敢不敢用，后者解决值不值得用。

## 四、存储约束（既定边界）：文件本地管理，无 OSS

决策（2026-09-12 确认）：**文件不落 OSS / 对象存储，一律本地管理**。依据：内网合规、成本、与 Bridge 本地执行和"加载本地项目"天然一致。

**三层本地架构**
1. 执行设备本地（Bridge 设备/用户电脑）：工作区、项目仓库、终端产物、沙箱快照——文件归属执行端，开发作业读写本地文件与 Git，浏览器只看结果。
2. 服务端本地目录（服务器磁盘）：材料库（上传附件）、产物基线快照、审计归档、知识库文件——统一目录规范，按需求/版本分目录。
3. 元数据库（SQLite/PG）：只存元数据——路径 · SHA-256 · 大小 · 类型 · 所属需求/版本 · 引用关系 · 权限。容量条、去重、检索、审计查库，不碰文件体。

**文件类型落位**

| 文件类型 | 存放位置 | 写入方 | 引用方式 | 容量/备份 |
|---|---|---|---|---|
| 项目/工作区 | 执行设备本地 | 开发 agent（Codex/Zed） | 路径 + Git 分支 | Git 承担版本；磁盘配额 |
| 上传材料/附件 | 服务端本地目录 | 用户上传 → 元数据入库 | 路径 + SHA-256 去重 | 配额；定时快照 |
| 产物基线/版本 | 服务端本地版本目录 | 确认版本时快照 | baseline 号 + 路径 | 按需归档，可设保留期 |
| 沙箱快照/回放 | 执行设备本地 | 作业执行时生成 | runId + 差异清单 | 与作业生命周期绑定 |
| 审计归档 | 服务端本地 | 动作落库 | 审计条目引用文件路径 | 只增不改 |

**补充措施**：目录规范与权限 · 哈希去重 · 备份归档任务 · 跨设备共享走 Bridge/内网共享目录（不复制文件体）。
**代价与缓解**：单点磁盘 → 快照备份/共享盘；多人协作 → 内网共享/Bridge（部门级足够）；横向扩展受限 → GB~TB 级完全够。

## 五、落地路线建议

1. **MVP 聚焦三阶段闭环**：需求 → 开发 → 验收（先别铺 8 阶段全量治理），chat 主作业 + 配置中心
2. **P0 五项先做**：计划审批硬门、客观质量门、复盘→知识库反哺、MCP/ACP 开放协议、SSO/租户
3. **存储按第五节既定边界**：本地文件管理，不引入对象存储
4. **工程分期**：M1 单机/内网可用（服务端会话 + LLM 网关）→ M2 Bridge 执行 + 沙箱回放 → M3 生态集成（Jira/飞书/CI/数仓）

## 六、与原型现状的衔接

- 原型已具备并验证（46/46 + 13 + 8 + 11 + 12 全绿）：8 阶段门控、13 项能力目录、治理中心（角色/权限/审计/预算/材料门/租约）、多 CAP 编排、跨阶段会话、本地项目加载、范围引用、容量条

- 已明确不做：对象存储（本地管理）、自研模型、移动端优先
