# POD-PFC-001 交付防偏航控制

> 版本：GOV-R1  
> 日期：2026-09-05  
> 状态：本地治理验证 PASS

## 1. 触发原因

当前实现完成了 `CAP-PFC-01` 的本地技术闭环，但连续以子任务 T1-T7 和 UI-R1-R12 为进度单位，没有在每次完成时回到 `POD-PFC-001` 检查 5 CAP、26 Unit 和 M1-M3。结果是临时 fixture/unavailable 依赖长期存在，并被用户界面体验误认为平台总体能力。

用户确认后续先治理再继续，并补充约束：本地 PostgreSQL 已可用，应持久化的业务事实必须持久化，不能长期使用演示数据造成偏离。

## 2. 选定控制

采用三层控制：

1. `AGENTS.md` 保存不可绕过的项目规则和结论边界。
2. `.quality-gate/delivery-plan.json` 保存 5 CAP、26 Unit、M1-M3、持久化政策、当前状态和唯一下一路线。
3. `check:delivery-governance` 机械校验范围、里程碑完成条件、fixture 结论、标准数据库目标和下一路线，并进入 quick/core/full。

不采用仅文档提醒，因为无法阻止重复偏航；暂不把治理能力做成业务页面，因为当前目标是恢复 M1，而不是新增治理产品范围。

## 3. 状态口径

| 状态             | 含义                                                   | 不能替代                  |
| ---------------- | ------------------------------------------------------ | ------------------------- |
| `LOCAL_VERIFIED` | 源码及本地自动化已验证                                 | 真实跨 CAP 集成、产品验收 |
| `INTEGRATED`     | 标准本地运行使用真实实现和 PostgreSQL 事实完成读写回环 | 产品验收、发布            |
| `ACCEPTED`       | 具名责任人按当前版本确认产品结果                       | 发布授权、业务最终效果    |
| `RELEASED`       | 明确环境完成获批发布并有 smoke/观察证据                | G12 业务验收              |

fixture、mock、`UNAVAILABLE` 端口、`pfc_experience`、测试报告和 dry-run 均不得提升上述状态。

## 4. 数据政策

- 标准本地业务事实：`pfc_local.pfc`。
- 自动化测试：确定性 `CODEx_TEST_` 数据，只进入进程内存或 `codex_test_*` 隔离 schema，结束后清理并读回。
- 历史体验模式：`pfc_experience` 在 M1 退出前退役，不计入任何 CAP 或里程碑。
- 治理台账：保存在源码仓以便无数据库环境也能运行 CI；它记录交付状态，不替代 PostgreSQL 中的业务事实。

## 5. 当前恢复点

- 当前里程碑：M1，`IN_PROGRESS`。
- 已有：PFC-01 五个 Unit 达到 `LOCAL_VERIFIED`，但真实依赖仍阻断。
- 缺少：`UNIT-PFC-02-01` 产物目录，`UNIT-PFC-04-01` 至 `04-03` 团队、角色和工作区，以及标准 `pfc` schema 的真实本地运行。
- 唯一下一路线：`POD-PFC-001/M1-R1/PFC-02+PFC-04-design`。

## 6. 验证与回滚

校验至少覆盖：删除任一 CAP/Unit、错误宣布 M1 完成、fixture 冒充真实集成或验收、改回内存业务状态、缺少 POD 下一路线时失败。最终运行 quick 和 core。

回滚仅反向编辑本轮治理文件；本轮不迁移数据库、不修改业务 API、不重置体验 schema、不安装依赖、不执行外部动作。
