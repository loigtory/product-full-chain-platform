# 产品方案：围绕需求连续推进的产品工作台

版本：V0.2 草案，2026-09-11。当前交互基线：[用户选定的原版](../../../output/pfc-workbench-prototype/index.html)；[V3](../../../output/pfc-workbench-prototype/index-v3.html) 作为补充状态对照，另依据已确认主 Spec V0.1/R3、AI-UX-D0/D1 及当前实现。状态：供产品与研发共同评审，不宣称 CAP Ready。

保留原版对话主体、AgentRun 卡、Zed 对话流和右侧终端/画布/证据的完整组合。原版当前可操作行为、演示限制和正式接入要求以 [开发交接](05-原版开发交接.md) 为准，V3 仅保留对照意义。

## 1. 定位、用户与成功结果

PFC 是面向产品经理及其协作角色的 PC 产品作业平台。用户从一条需求出发，连续完成问题澄清、产物编写与确认、研发作业、测试验收、发布观察和复盘。平台负责把上下文、版本、责任和结果连在一起，AI 参与整理与执行，人对产品决策和交付结论负责。

当前最需要解决的三个问题：

1. 不知道今天先处理什么：进入首页即可看到待回答、待确认、被阻断和需要恢复的事项。
2. 同一需求的工作分散：在需求工作区内查看来源、讨论、草稿、任务和证据，切换后不丢位置、不串需求。
3. 页面说“完成”却找不到依据：每项完成状态可以定位到同版本的确认、运行结果或验收证据。

| 角色                  | 主要工作                                           | 关键权限与责任                             |
| --------------------- | -------------------------------------------------- | ------------------------------------------ |
| 产品经理 / 产品负责人 | 登记、澄清、确定范围、维护文档、发起作业、组织验收 | 只操作负责或获授权需求；确认明确版本与范围 |
| 研发 / 获授权执行者   | 确认技术方案、实施、处理失败、交接测试             | 代码与命令执行受工作区和动作授权约束       |
| 测试 / 验收负责人     | 测试映射、执行结果、缺陷处理、产品验收             | 测试通过与产品验收分别记录                 |
| 发布 / 业务责任人     | 发布范围、回滚、观察与最终业务结果                 | 发布授权、发布执行、业务最终验收分别记录   |
| 团队管理员            | 成员、角色、工作区、Bridge、能力策略与审计         | 配置可用范围；不能用配置替代某次执行授权   |

现阶段陈立承担多个责任角色是已接受的本地安排；仍需分别记录每类结论。目标产品支持团队分工，原型中的单一头像不代表所有人共享账号。

首期成功结果沿用主 Spec：一个真实但非生产写入需求形成 G0–G12 连续证据；Web/Zed 能定位同一作业；中断恢复不重复副作用；未授权动作被拒绝。原型演示、界面状态和模型回复不能独立满足这些条件。

## 2. 信息架构与页面职责

保留原版四个一级入口，以及“左侧上下文 / 中央对话与任务卡 / 右侧结果”的工作区。1280/1440/1920 PC 宽度保持三栏；长文档支持聚焦阅读。业务页沿用 `packages/ui` 的统一控件与三层视觉变量。

| 入口       | 首屏回答的问题             | 内容与主要动作                                                        | 对应业务能力                   |
| ---------- | -------------------------- | --------------------------------------------------------------------- | ------------------------------ |
| 我的工作台 | 现在需要我做什么           | 我的待办、被阻断事项、运行任务、最近需求；一键返回具体问题/版本/作业  | CAP-01，聚合 CAP-02/03/05      |
| 产品空间   | 这个产品有哪些需求与成果   | 需求清单、产品上下文、当前与历史产物、关系追踪；进入同一需求工作区    | CAP-01/02，团队边界来自 CAP-04 |
| 交付中心   | 哪些交付还差什么           | 需求/CAP/版本的测试、验收、发布与观察摘要；下钻到事实记录             | CAP-03/05，复用 CAP-01/02      |
| 治理中心   | 谁能在什么范围使用哪些能力 | 团队角色、工作区与 Bridge、Skill/MCP/工具可用性、阶段策略、审批与审计 | CAP-04，协作 CAP-02/03         |

四个入口共享事实。首页待办是对问题、评审、审批、失败任务等对象的查询结果；交付中心是交付事实的汇总。二者不单独保存一套“完成/未完成”状态。

原版产品空间现在按当前演示团队与需求动态汇总。正式首版先基于已登记团队与需求提供聚合视图；产品若需独立成员、生命周期和跨团队范围，再单独确认实体规则，不能把示例名称当作已实现产品域。

| -------- | ---------------------------------------------- | -------------------------------------------------------- |

## 3. 八个阶段与 G0–G12 的关系

下面是**建议的产品投影规则，待确认**。保留八阶段名称，同时展示对应门禁与检查点。一个门禁可以包含多个用户任务，不新增第二套权威生命周期状态。

| 用户阶段 | 对应控制点                       | 用户要完成什么                             | 转入下一用户阶段的条件                               |
| -------- | -------------------------------- | ------------------------------------------ | ---------------------------------------------------- |
| 想法     | G0–G2                            | 登记来源、确认问题、目标和处理结论         | 需求处理结论明确并进入范围梳理                       |
| 需求     | G3–G5                            | 范围、CAP/Unit、估算输入、涉研结论         | 当前版本范围及估算评审形成结论                       |
| 设计     | G6–G8；G9-A 技术方案确认前的工作 | 设计输入、原型、正式 Spec、技术方案        | 当前 CAP 的 Ready 输入及技术方案已确认               |
| 开发     | G9-A 实施、G9-B 提测交接         | 实现、工程验证、整理同版本提测材料         | G9 两个检查点均满足，进入 G10                        |
| 测试     | G10 测试任务                     | AC 映射、测试执行、缺陷及未测范围          | 所需测试满足进入产品验收的条件；G10 仍未因此自动通过 |
| 验收     | G10 产品验收任务                 | 负责人核对可见结果、风险和验收结论         | 测试及产品验收所需结论齐全，G10 通过                 |
| 发布     | G11 准备、审批与执行             | 确认准确版本、目标、范围、回滚并执行       | 有发布结果证据后进入观察；G11 仍需观察完成           |
| 观察复盘 | G11 运行观察、G12 业务最终验收   | 观察窗口、目标与实际结果、遗留项及后续决策 | G11 观察及 G12 业务责任人结论齐备                    |

正式阶段导航的状态由门禁和检查点事实推导。G9 的“设计/开发”、G10 的“测试/验收”、G11 的“发布/观察”不能只靠一个门禁编号判断，需要读取对应确认和结果。缺少明细时显示“待核验”，不猜测已完成。具体投影契约必须在代表页设计前确认。

CAP/POD 下可能有多个并行 CAP。需求概览应显示 CAP 进度和阻断，进入具体 CAP 查看其版本与检查点；单个 CAP 通过不会让整个 POD 的阶段全部变绿。首轮代表页可选单 CAP 需求，整体验收仍覆盖多 CAP 汇总规则。

## 4. 核心工作流程

### 4.1 从想法到可确认产物

用户登记原始想法与来源，系统创建需求和材料基线。产品 Agent 根据授权上下文提出澄清问题，用户填写回答并确认解释。回答形成 Question/Decision；补充文档的建议呈现明确字段变化，经确认后生成新的 ArtifactVersion。

原版已补齐新需求入口、材料登记和空工作区，可以从零开始走查；PDF/Word/图片仅登记元信息，真实解析和持久化仍需正式接入。材料至少表达来源、用途、敏感级别与允许使用范围；进入 AI 上下文前完成相应检查。

### 4.2 产物修改与确认

1. 用户打开具体产物和版本，查看正文与来源。未归档正文时明确提示，不能用空白冒充原文。
2. AI 或用户提出修改，显示准确比较版本和变更内容。
3. 保存创建新版本，旧正文保留；确认记录绑定版本 ID、正文哈希、角色和时间。
4. 同时有人更新目标时，阻止覆盖，保留未提交内容并引导比较最新版本。
5. 已确认版本需要修改时，创建后续草稿；旧评审仅对旧版本有效。原型目前只读的已确认状态需要补充此入口。

结构化字段对比适用于需求表单；Markdown/文本正文使用版本全文或行级差异。首期采用既有 R3 的受控文本方案，不因原型表格而要求重建富文本编辑器。

### 4.3 发起与处理 AI 作业

普通对话由 ProductWorkTurn 处理，产出可审查建议。需要修改文件或运行命令时创建 AgentRun，明确需求、CAP、版本、工作区、基线、Skill 和动作范围。页面给出具体不可用原因，例如未登记工作区、Bridge 离线、能力版本不匹配或材料传输待授权。

本地 Shell、文件和 Git 工具属于平台基础执行能力。目标体验是用户在同一对话说“查看项目代码”“运行测试”或“启动本地预览”，平台通过选定电脑的 Bridge 执行，并在任务卡中返回输出、退出码、文件差异或预览地址。已有任务授权范围内的操作连续完成，无需用户手工复制命令或逐条重复确认；范围变化时说明新增操作及原因。预览进程提供状态与停止入口。

现有真实作业契约仅提供产物检查和受控产物编辑。原型中的代码实现、测试执行和发布卡片是目标场景，后续需补相应作业类型、输入输出契约、权限和验收证据。

| 操作/状态      | 正式产品语义                                                 | 原型需要调整的地方                   |
| -------------- | ------------------------------------------------------------ | ------------------------------------ |
| 停止运行       | 提交取消请求，先显示“正在停止”；收到执行侧结果后显示“已取消” | 不应点击即认定执行已停止             |
| 取消后继续     | 先核验旧结果，再创建关联旧作业的新尝试；重新校验版本与授权   | 不将已取消终态直接改回运行中         |
| 等待输入/审批  | 当前作业保持等待；合法输入或批准后由执行侧续行               | 不与“已取消”混为暂停                 |
| 结果未知       | 显示最近事件和核验入口，阻止重复执行                         | 增加 UNKNOWN 分支                    |
| 完成           | 作业终态、结果及证据归档状态分别可见                         | 100% 进度不能代替成功或归档完成      |
| 无可靠进度比例 | 显示当前步骤、已完成项和运行时长                             | 不显示由定时器或固定步数计算的伪进度 |

### 4.4 测试、验收、发布与复盘

测试结论来自同版本 TestRun/检查结果与 AC 映射；产品验收由责任人核对结果并确认。发布准备引用已验收版本，审批只批准精确目标和范围，执行单独记录。执行完成后进入观察，业务最终验收比较原始目标与实际结果，记录遗留项和下一决策。

首个端到端试点使用非生产目标和真实可核验的本地执行证据。发布演练必须标明演练，不作为生产上线记录。没有实际指标时显示“待采集/无数据”，不沿用 V3 的 96.8%、3.1% 等固定示例。

## 5. 能力配置与实际可用性

保留“能力目录 / 阶段绑定 / 本次会话调整”三层体验，建议正式规则如下：

1. 能力目录聚合 Skill 版本、已登记只读 MCP 和工具可用性。展示真实来源、版本、适用范围及运行时状态。
2. 阶段绑定提供团队默认策略。原型中的“全局”在首期解释为当前团队作用域，不默认跨所有团队生效。
3. 本次会话调整只影响该需求会话的后续回合；不能启用策略禁止或运行时不可用的能力。
4. 每个回合/作业保存执行时能力快照。后续配置变化不篡改历史，也不悄悄替换运行中的版本。
5. 全局/团队停用立即阻止新调度；已开始任务继续受原授权、撤销与取消机制控制。紧急停用是否终止运行需在对应动作预览中明示。

启用、已安装、在线、已授权是不同含义。目录开关不自动安装 Skill、登录 MCP 或授权外部动作。V3 中“飞书文档/MCP 市场/VS Code”等名称是示例；真实连接、市场安装和新增 IDE 范围不能从名称推导。

## 7. 首期边界与衡量方式

V0.1 保留原 5 CAP / 26 Unit。移动端、通用 IDE、中心 Agent 集群、市场自动安装、额外 IDE 集成、SSO 和默认生产自动化均不在本方案首期实现范围。相关需求有依据后单独评审。

| 观察指标     | 计算或核验口径                                                    | 当前基线                       |
| ------------ | ----------------------------------------------------------------- | ------------------------------ |
| 任务成功率   | 预定任务中，用户在无需搬运上下文的情况下完成的任务数 / 执行任务数 | 待代表页测量                   |
| 关键操作耗时 | 从打开待办到完成回答/确认/恢复的时间，按任务类型记录              | 待测，不承诺提升比例           |
| 确认返工     | 因版本不清、上下文错误而撤回或重新确认的次数                      | 待测                           |
| 证据完整性   | 当前阶段必需证据是否全部关联准确版本；缺失项必须可见              | 按门禁逐项验证                 |
| 状态可信性   | 越权执行、旧版本覆盖、重复副作用、伪成功场景是否被阻止            | 作为退出阻断项，不能由均分抵消 |

验收先检查业务正确性与恢复能力，再做三档桌面视觉确认。产品经理看到的下一步、服务端允许的动作和最终持久化结果必须一致。详细 Unit 覆盖与阶段退出标准见[路线图](03-路线图.md)。
