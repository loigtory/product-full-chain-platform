# 49. 命令隔离实测结论与方案调整-20260917

> 交接线：48 > 47 > 46 > 45。本文档记录"命令隔离方案（AppContainer 沙箱）"的实测过程与结论，以及由此触发的方案调整建议。
> 状态：**待确认**（方案调整需用户决策后实施）

## 1. 背景

48 号文档授权了三项一次性系统配置以实施命令隔离方案：
1. AppContainer profile 注册（`pfc-exec-hz19114673`，SID=S-1-15-2-708689038-3107316110-4090110287-4211596437-971289818-2082749301-4002726801）
2. pinned node/git 入沙箱 tools
3. 保持 PG Stopped

方案目标（对齐 44 号"受限读目录 + 允许文件/命令 + 基线和撤权复核"）：沙箱进程获得三个可实证边界——
- **读边界**：工作区 + tools 可读，用户私有目录不可读
- **写边界**：仅工作区可写
- **网络边界**：无 capability，不可连接（含外网）

## 2. 实测过程与结果

### 2.1 环境事实（前置确认）

| 项 | 结果 |
|---|---|
| OS | Windows 10.0.26100（x64） |
| 当前用户 | `oa\hz19114673`，**非管理员**（IsInRole(Administrators)=False） |
| D:\ 根 ACL | `BUILTIN\Administrators(F)`、`Authenticated Users(M)`、`Users(RX)`；**icacls 修改被拒**（非管理员） |
| C:\Users ACL | SYSTEM/Administrators/用户本人；**不可修改**（非管理员） |
| AppContainer API 位置 | `CreateAppContainerToken` 实际导出在 **KernelBase.dll**（无后缀）；`ConvertStringSidToSid` 在 advapi32 仅 A/W 后缀；kernel32/advapi32 均无 `CreateAppContainerProfile` 导出（API set 布局与常规文档描述不同） |

### 2.2 关键实验与结论

| # | 实验 | 结果 | 结论 |
|---|---|---|---|
| 1 | CreateAppContainerProfile 注册（普通用户） | HRESULT=0，注册表映射确认 | ✅ 普通用户可注册 AppContainer profile |
| 2 | CreateProcess + STARTUPINFOEX + SECURITY_CAPABILITIES（AppContainerSid，空 capabilities）启动 node | 进程启动成功，node --version 输出 v22.23.2 | ✅ 进程可启动（ac-run.ps1 runner） |
| 3 | 沙箱内 `whoami /groups` | 组列表 = 普通用户（BUILTIN\Users 启用、无 Package deny 组、**Medium 完整性级别**） | ❌ **进程令牌为普通令牌**，AppContainer 隔离未生效 |
| 4 | 读边界：用户 Documents / Temp / D:\ 根 / C:\Windows\win.ini | **全部可读**（含用户私有 Documents） | ❌ 读边界不存在 |
| 5 | 写边界：用户 Temp / D:\ 根 / System32 | **Temp、D:\ 根可写**（System32 被拒=普通用户无权限） | ❌ 写边界不存在 |
| 6 | 网络：127.0.0.1:19001（确认监听）/ 8.8.8.8:53 | **全部可连接** | ❌ 网络边界不存在（capabilities 未生效） |
| 7 | 令牌检查 GetTokenInformation(30) | 返回异常（NULL_SID / SID2STR_ERR=1337） | 佐证令牌无有效 AppContainer SID |
| 8 | 替代路径 CreateAppContainerToken（KernelBase） | **原生崩溃**（访问冲突） | 该路径在本环境不可用 |

### 2.3 根因分析

- **SECURITY_CAPABILITIES 属性静默失效**：CreateProcess 返回成功、子进程可执行，但令牌为普通用户令牌。已核对结构布局（STARTUPINFOEX=112B、SECURITY_CAPABILITIES=24B）、属性常量（0x20009）、EXTENDED_STARTUPINFO_PRESENT 标志，均无误。结合 #1 中 AppContainer API 不在标准导出位置的观察，**本系统（26100）的桌面 AppContainer 行为与文档描述存在差异**，未继续深挖（性价比低）。
- **即便 AppContainer 生效，文件系统隔离也不成立**：实测证据表明该环境下 AppContainer 进程的文件访问 = 常规 DACL 检查（用户 SID/组 allow 有效），能读用户私有目录、能写用户可写位置。这与 UWP 包的"默认 deny 用户目录"不同——桌面 AppContainer 无此机制。

## 3. 方案调整建议

### 3.1 已否决路径

| 路径 | 否决原因 |
|---|---|
| AppContainer 沙箱（当前） | 实测文件/网络边界均不成立（见 §2） |
| Restricted Token（受限令牌，文件隔离） | 受限 SID 双检查要求**路径链每级**有受限 SID 授权；D:\ 根与 C:\Users ACL 不可改（非管理员），工作区无法被受限进程到达 |
| Windows Sandbox / VM | 需管理员 + 功能启用，不可行 |

### 3.2 推荐路径（审批流驱动的执行控制）

**放弃进程级文件/网络隔离，以流程控制为核心**——这与 Codex / Claude Code 等本地 agent 工具的实际模型一致：

1. **命令白名单 + 审批流**（对齐 44 号"冻结计划、允许文件/命令、基线、撤权复核"）：
   - 可执行命令 = 白名单（node、git、npm test 等）∩ 用户逐条审批
   - 敏感命令模式拦截：`git push`、`rm -rf`、`curl` 外发、读取密钥路径等默认拒绝，需显式授权
   - 审批记录完整留痕（谁、何时、批准了哪条命令）
2. **Job Object 进程树管理**：
   - 一次性作业，超时（默认 300s，与 46 号文档一致）强制终止整树
   - 取消命令 = 终止作业对象（补齐 codex 纠偏 #3 的"停止与恢复未接通真实任务"）
3. **可审计执行**：每条命令的执行时间、退出码、输出摘要、变更文件指纹入库
4. **网络策略（可选增强，后续）**：HTTP(S)_PROXY 白名单代理，仅放行 npm registry、git 远端等必要域名

### 3.3 备选路径（如用户要求严格文件隔离）

需**管理员提权一次**（修改 D:\ 根与 C:\Users 的 ACL 增加包 SID 授权），或改用容器/VM 方案。涉及用户环境变更，需单独授权。

## 4. 本方案与已授权配置的关系

- AppContainer profile（`pfc-exec-hz19114673`）已注册，**保留**（无副作用，可在网络隔离增强时复用）
- pinned node/git 入沙箱 tools：**改用于审批流执行器的 pinned 工具链**（版本固定，防止 PATH 注入）
- PG 保持 Stopped：不变
