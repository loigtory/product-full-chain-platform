## 3. 已选方案

采用 G9-A 已确认的模块化单体和右侧问题抽屉，不引入第二套状态来源：

1. `packages/contracts` 增加 Question/Decision DTO 与五类命令请求；Requirement 详情携带当前 baseline 的问题及决定历史。
2. `packages/domain` 补齐 Question 的原因、候选和决定类型；状态转换仍由 `transitionQuestion` 约束，不允许跳过 ANSWERED 确认。
3. `apps/server/questions` 负责应用服务与 HTTP 路由；授权先于问题正文读取。回答使用 `ANSWER_QUESTION`，确认、退回、替代和延后使用 `CONFIRM_QUESTION`。
4. `packages/persistence` 在一个事务内完成 Question/Decision、幂等记录、时间线和 outbox 写入；Question 行锁和 rowVersion 是并发最终防线。
5. `apps/web` 在需求详情右侧抽屉展示问题、候选、原始回答、解释、作用域、确认信息和历史，不从浏览器状态推断成功。

## 4. 决定与历史语义

- 回答：OPEN -> ANSWERED，追加 ANSWER Decision；新回答不覆盖被退回的旧回答。
- 确认：ANSWERED -> CONFIRMED；只为当前 Decision 补充确认角色、确认人和确认时间。相同命令幂等重放，不产生第二次关闭。
- 退回：ANSWERED -> OPEN；保留 current Decision 和原始回答，退回人/原因记录在权限保护的 TimelineEvent；outbox 只带状态摘要，不带原因或回答正文。
- 替代：已有 CONFIRMED Question/Decision 变为 SUPERSEDED；创建新的 CONFIRMED Question 和 ANSWER Decision，新 Decision 反向引用旧 Decision。旧记录不删除。
- 延后：OPEN/ANSWERED -> DEFERRED；追加 DEFERRAL Decision，原始回答字段承载不阻断理由、解释字段承载重新进入条件，并以 `kind=DEFERRAL` 明确区分。

## 5. 接口与错误

- `POST /api/v1/requirements/{id}/questions/{questionId}/answers`
- `POST /api/v1/requirements/{id}/questions/{questionId}/confirmations`
- `POST /api/v1/requirements/{id}/questions/{questionId}/returns`
- `POST /api/v1/requirements/{id}/questions/{questionId}/supersessions`
- `POST /api/v1/requirements/{id}/questions/{questionId}/deferrals`
- 查询继续使用 `GET /api/v1/requirements/{id}`；响应包含 Question/Decision 权威状态，供正常展示和 UNKNOWN 核验。
- 继续使用稳定错误 `VALIDATION_FAILED`、`PERMISSION_DENIED`、`VERSION_CONFLICT`、`IDEMPOTENCY_CONFLICT`、`RESULT_UNKNOWN` 和 `INVALID_STATE_TRANSITION`；错误体不得包含问题、回答、退回原因或内部堆栈。

## 9. 风险、回滚与停止条件

- 风险：确认错绑旧 Decision、回答被覆盖、替代删除历史、越权前读取正文、重复确认、UNKNOWN 盲重试、outbox 泄露回答。
- 回滚：仅反向编辑本轮未提交 T4 文件；不使用 destructive Git，不删除默认 schema 或非测试数据。
- 停止条件：需要改变已确认产品行为、无法在同事务保留历史、出现无权正文读取、Question 动作改变 Requirement 阶段/GateRun、测试写入非隔离 schema，或出现未解释的依赖/资源异常。
- 本轮不使用并行代理；完成后关闭 dev server、浏览器和测试 runner，并报告保留的本地 PostgreSQL 服务。
