# 54-阶段冻结接入真实执行链实施与验收-20260918

> 承接：53 号待办「真实执行链路：仍由 50 号 command-runner 审批流 + 52 号冻结计划接管（未做真实模型调用）」——54 号把**阶段冻结计划（stage_plans）接入 EXECUTE 作业的真实执行约束链**。
> 状态：**已实施，HTTP 验收 17/17 PASS**（零模型，作业停在 QUEUED）。改动**已提交 git**（commit `见文末`）。

## 一、背景与决策

- 53 号只扩展了**前端**（exec-bar 条件 dev → design/dev/test），服务端 EXECUTE 分支仍硬编码 `stage !== 'dev'` 才放行；且 52 号冻结计划（stage_plans）只做了 UI 化，**没有成为真实执行的约束来源**——作业的 control 仍来自 turn 级 freezeForActor（50 号 approve 流）。
- 54 号目标：**冻结计划 = EXECUTE 作业的执行约束权威**：
  - 阶段对齐：EXECUTE 触发条件从 dev-only 放宽为 design/dev/test 三阶段（与 53 号前端一致），并要求 `row.stage === stage` + owner 角色；
  - 计划派生：当前阶段存在 frozen plan → control 由计划派生（工作区/基线/有效期校验 + `approvalSource='STAGE_PLAN'`）；revoked → 拒绝（`PLAN_TERMINATED`）；无 plan → 回退 50 号 freezeForActor（兼容既有审批流）。

## 二、实施内容

### 2.1 `server/src/agent/stage-plan.js` — 新增 `deriveExecControl(db, ctx, req, stage, input, contextHash)`

```text
1) STAGES 校验 → STAGE_INVALID(400)
2) 查 stage_plans（tenant_id + req_id + stage）
   - 无记录 → 回退 execControl.freezeForActor（50 号 approve 流，approvalSource=SERVER_AUTHENTICATED）
   - state≠frozen → PLAN_TERMINATED(409)
   - 工作区 path.resolve 大小写不敏感比对不一致 → PLAN_WORKSPACE_MISMATCH(409)
   - 基线哈希（scanWorkspace+baselineHash）不一致 → PLAN_BASELINE_CHANGED(409)
   - 计划 validUntil 已过期 → PLAN_EXPIRED(409)
   - 通过 → validatePlan 派生：mode/allowedFiles/allowedCommands/forbidden/maxFiles/maxBytes
     取自冻结计划；validUntil 重算为 turn 级 5 分钟；approvalSource='STAGE_PLAN'；
     approvedBy=row.created_by；reqId/tenantId/contextHash 注入
```

### 2.2 `server/src/agent/exec-control.js` — validatePlan 身份校验放宽

- 原：`control.approvalSource !== 'SERVER_AUTHENTICATED'` → 拒绝 STAGE_PLAN 派生控制（PLAN_IDENTITY_REQUIRED）；
- 改：`!['SERVER_AUTHENTICATED', 'STAGE_PLAN'].includes(control.approvalSource)` —— 阶段计划派生与 50 号 approve 流两种来源均合法。

### 2.3 `server/src/domain/conversation-service.js` — EXECUTE 分支三阶段对齐 + 计划派生

### 3.1 排查记录（重要，避免复踩）

1. **`expectedRevision` 字段名**：message POST 的版本校验用 `input.expectedRevision`（不是 `revision`）；verify 脚本初版传错导致 REVISION_REQUIRED×4。
2. **已 frozen 再 freeze = 触发器 23514**：008 `stage_plans_guard` 对「非 revoked→frozen 的契约字段变更」RAISE `STAGE_PLAN_INPUT_IMMUTABLE`（无 HTTP status → 降级 503 STORAGE_UNAVAILABLE）。**这是设计预期**：重复 freeze 必须先 revoke（新周期）。验证脚本需用全新数据，不能复用已冻结需求。
3. **freeze「写库成功但响应 503」偶发**：首轮验证 C(design) freeze 返回 503 但 stage_plans 记录已提交（created_at 存在）。证据指向 PG 连接池（`max:2` + `statement_timeout:3000` + `idleTimeout:1000`）在特定时序下的 COMMIT 不确定/超时——**无 status 错误统一被 index.js 降级 503**。未在后续轮复现，记录为已知基础设施风险（见四-2），非 54 号功能缺陷。
4. **approvalSource 两处 bug**：① deriveExecControl 初版把计划派生标成 `SERVER_AUTHENTICATED`（应为 STAGE_PLAN）；② validatePlan 身份校验只认 SERVER_AUTHENTICATED（STAGE_PLAN 被拒 PLAN_IDENTITY_REQUIRED）。均已修复。
5. **诊断脚本 mock db 缺 `assertScope()`**：withTransaction 依赖 `db.assertScope()`，直调 freeze 的诊断需用 runtime.db() 或补该函数（非产品缺陷）。
6. **清理注意**：删测试数据需先 DISABLE 审计触发器（stage_plans_guard / agent_jobs_guard / agent_events_immutable / req_versions×3），且 agent_jobs 有子表 FK（agent_events 等）——用 SAVEPOINT 隔离逐表删，最后删 reqs（本次 18 需求 + 关联数据已全清）。
