## 一、目标

「设计确认 → 推进开发」增加**质量门禁**：confirm-design 放行 dev 之前，强制校验四类设计产物（方案设计文档 / 时序图 / 流程图 / 可交互原型）**齐套且格式达标**。缺失或不达标 → 阻断推进并逐项列出缺口（缺证据不得声称可进入开发）。

与 64 号关系：64 号解决「设计产物能否真实产出并沉淀」，65 号解决「没有产物时是否被放行」——前者是能力，后者是纪律。

## 二、本次改动

### 唯一改动点：`server/src/domain/artifact-confirmation-service.js`（DESIGN 分支）

`confirm(id, gid, input, 'DESIGN')` 在既有前置校验（阶段对齐 / business 确认 / designVersionId 匹配）通过后、正式落库前插入门禁：

```text
const da = await require('./design-artifact-service').listForReq(db, ctx, req.public_id);
required = ['design', 'sequence', 'flow', 'prototype']
missing = required.filter(k => !da[k])                       // 缺失产物
formatIssues = []                                            // 格式校验：
  design     → 必须含「背景与目标|背景」与「总体架构|架构」章节
  sequence   → 必须含 sequenceDiagram 标记
  flow       → 必须含 flowchart 标记
  prototype  → 必须含 <html 与 <input 与 <button 交互要素
任一缺失或格式不达标 →
  access.fail('DESIGN_ARTIFACTS_INCOMPLETE', 409,
    ['缺 design；缺 sequence；…；格式问题；请先在设计阶段完成 EXEC 作业产出四类产物，或人工补录后重试'])
```

- 复用 64 号 `design-artifact-service.listForReq`（公共 reqId 查询最新快照），无新增表 / 无迁移。
- 格式校验为**最小可达性检查**（mermaid 标记 / HTML 交互要素 / 方案章节关键词），不评判质量优劣——质量由 EXEC 阶段所选 skill 与人工评审保障。
- 阻断发生在**确认事务内**（artifacts.mutate 回调），异常即中止，不写任何确认记录、不推进版本。
