M2c 的完整目标仍为 19 号的治理、发布、项目领域模型与 PG 存储适配。没有增加框架、服务或新依赖。实现继续使用原生 JS、Express、现有 pg/WS；能力登记保存元数据，不安装程序、不运行 endpoint 命令。

| 当前事实及代码依据 | 对实施的影响 |
| --- | --- |

## M2c-1 待确认设计与精确范围

### 存储设计

1. 只增加 `server/src/persistence/` 内的连接、事务和仓储组件，复用现有 pg。此轮不切换 Express 的现有 `db.js`、`index.js`、service 或 WS 路径，避免把部分仓储完成写成应用已使用 PG。
2. 新连接组件明确区分 memory 与 pg；显式 pg 下缺配置、连接失败或迁移未准备好均报错，禁止隐式回退。连接只做连接/就绪检查，不能执行 DDL；迁移工具与测试工厂显式调用迁移。旧 `db.js` 的降级逻辑在 M2c-2 切换前仍属已知缺口，不声称本轮已修好它。
3. 保留 SQL 草案的 UUID 主键，对已落表实体增加 `public_id` 文本及租户内唯一约束；内部引用使用 UUID，对外继续原编号。需求号分配用库内计数记录与事务，不能用进程内 seq 或数组长度。同一文本 ID 的跨实体映射不得互串，重启后仍可解析原编号。
4. 最小验证表为 `tenants`、`reqs`、`req_versions`、`audit_logs`，另加 schema 内迁移版本表、编号计数表。只落需求/版本/审计的明确字段；版本正文可用既定 `content jsonb`，禁止将整棵前端状态塞入一个 JSON 字段冒充领域落表。其他表及应用切换留下一轮。
5. 需求及其初始版本/审计同事务提交；失败回滚，包括编号分配。要求阶段版本的 `(req_id, stage, version)` 唯一；测试并发创建和事务失败后重试。actor/tenant 作为显式仓储上下文传入；本轮只是组件隔离验证，不因此宣称 HTTP 身份和多租户已安全。
6. 迁移使用版本号和 checksum，同一版本重复执行无变化，checksum 不一致拒绝；在事务内执行。Node 自带 `crypto.randomUUID()` 生成 UUID，不安装 pgcrypto/pgvector 扩展，不改数据库级对象。连接池上限 2、连接与 SQL 超时明确配置，错误日志仅打印安全类别，不输出连接串/密码。
